## Principal-engineer review: follow-ups and how to make each design more efficient

- **A1 / A2:** `thirdMax` keeps three `long`s; a sentinel inside the `int` range is a bug (`Integer.MIN_VALUE` is a legal answer); the general "k-th distinct" is a bounded min-heap or a `TreeSet` of size k (O(n log k)). One-flip ones generalises to "at most k flips" with the same window (count zeros, shrink while > k); for a stream you cannot rewind, remember only the previous run length (`prev`, `cur`). Flowerbed is a local greedy because planting earlier never blocks a later better choice; counting by gaps (`(gap - 1) / 2`) is the closed form. `MovingAverage` needs a `long` sum (or a Kahan sum for doubles) and a ring buffer: no `LinkedList`, no per-call allocation; a sliding median is a different problem (two heaps/TreeSets, see 2026-11-07). `RecentCounter` is a monotonic queue where each element enters and leaves once; with many windows or a huge rate, keep counters per second bucket (O(window) memory, not O(events)). `backspaceCompare` from the back is O(1) space because a `#` only affects characters to its left; the stack version is the easier first answer, say both.
- **B1:** one collector chain each; `groupingBy(classifier, TreeMap::new, downstream)` is the idiom for ordered keys, `collectingAndThen` for post-processing (`Optional` unwrap, `List.copyOf`). `maxBy` with a comparator that ends in `reverseOrder()` on the name makes the alphabetical tie-break explicit (never rely on encounter order of a `HashMap`). `honourRoll` uses `summarizingInt` once per student (average and count in one pass) and sorts only the survivors. `partitioningBy` always emits both keys, `groupingBy` with a predicate does not; that is the difference tests check. Averaging averages is wrong, keep sum and count. For data that does not fit in memory this is a keyed aggregation job (per-student state), not a list.
- **C1:** the tree DP is a post-order fold; making it iterative (pre-order list reversed) removes the stack-overflow risk of a degenerate tree and is easy to explain: every parent appears before its children in pre-order, so walking backwards visits children first. `IdentityHashMap` is used because `TreeNode` has no `equals`; an index-based array is faster and uses less memory if you number the nodes during the traversal. Rob III returns two numbers per node because "take" forces "skip" below and "skip" allows either; a single number needs memoisation by node to avoid exponential time. `maxPathSum` separates "best path bending here" (answer candidate) from "best downward chain" (what the parent may extend), and clamps negative branches to zero. `goodNodes` is top-down: carry the path maximum; ties count (>=). Use `long` for sums, the answer can exceed `int`. For a tree stored as parent pointers or an array, the same bottom-up order is the reversed BFS order.
- **C2:** `findDuplicate` views `i -> nums[i]` as a functional graph; the duplicate has two incoming edges, so it is the cycle entrance. Floyd is O(1) space and does not modify the array, the alternatives are sort (modifies, O(n log n)), a `HashSet` (O(n) space), swap-to-position cyclic sort (modifies), and the bit-counting method (O(n log n), also O(1) space). The cycle entrance proof: if the entrance is `a` steps from the head and the meeting point `b` steps past the entrance on a cycle of length `c`, then `2(a+b) = a + b + k c`, so `a = kc - b`, i.e. `a` steps from the meeting point also reaches the entrance. `topKFrequent`: bucket sort is O(n) and the heap alternative is O(n log k); for a stream use a count-min sketch plus a heap, or Space-Saving for approximate heavy hitters; with `Integer.MIN_VALUE` keys avoid array-index tricks on the values themselves.
- **D1:** sweep line: 2n events sorted by (x, signed height), a multiset of active heights (`TreeMap` with counts; a `PriorityQueue` with lazy deletion is the same O(n log n) with a smaller constant but trickier correctness). The signed-height trick encodes the three tie rules: at one x, starts before ends, taller starts first, shorter ends first; this avoids a spurious dip when two buildings touch and emits at most one point per x. Heights are compared with `Integer.compare`, never subtraction (overflow near 10^9 is fine but coordinates up to `Integer.MAX_VALUE` are not). Alternatives: divide and conquer merging two skylines (O(n log n), natural for parallel/MapReduce), or coordinate compression plus a segment tree with "chmax" range updates (useful when queries interleave with updates). Memory: sorting 200k `int[2]` allocates; for 10^7 events sort packed `long`s (`x << 32 | encoded height`).
- **E:** SINGLE_TABLE is the fastest hierarchy mapping (no joins, polymorphic queries are one table scan with a discriminator filter) at the cost of nullable subclass columns and a wide table; JOINED gives constraints per subtype but joins on every read; TABLE_PER_CLASS makes polymorphic queries a UNION. `type(n) = EmailNotification` becomes `where channel = 'EMAIL'`; the discriminator needs an index only if you query by it alone, here `(user_id, created_at)` serves the inbox query and the tie-break `id desc` makes pages stable (without a unique tie-break rows can repeat or vanish between pages). Offset paging is O(offset): at scale use keyset paging (`created_at < :cursor`) and skip the `count(*)` query (`Slice`). `@Modifying` bulk updates bypass the persistence context and the dirty-checking: flush first, clear after, and they skip `@Version` and listeners (add `version = version + 1` if the entity is versioned). `markRead` needs no `save()` because the entity is managed inside the transaction and flushed on commit; a bulk update is right for "mark all" because loading thousands of entities to flip a flag is wasteful. The owner-scoped lookup `findByIdAndUserId` returning 404 for someone else's row avoids leaking existence (IDOR). `@Value` with a default is fine for one number, a `@ConfigurationProperties` record is better for a group (validated at startup). `ResponseEntityExceptionHandler` already turns missing header, bad type and method-validation failures into 400 ProblemDetail, so only domain errors need handlers; 422 for a well-formed request with a semantically invalid target. In production also add an index on `(user_id, read_at)` for the unread count (or maintain a counter row) and a retention job (`staleUnreadEmailIds` is its seed).
- **F1 / G:** model comments as an adjacency list keyed `(post_id, parent_id, sort_key)` plus a materialised path (`/12/57/91`) or depth + root id so a whole thread loads in one range scan and subtrees by prefix; closure tables make subtree queries easy but cost O(depth) rows per insert. Vote counters on a hot comment must not be one row-update per vote: count votes in a per-user vote table (primary key `(comment_id, user_id)`, which makes retries idempotent) and aggregate asynchronously into a score kept in a sharded counter or Redis `ZSET` per post; the read path serves "Top" from a cached ranked list rebuilt every few seconds (Wilson lower bound, or score with time decay) so ranking cost is amortised across readers. Paginate with cursors `(score, id)`, never offsets, and load replies lazily (first 3 children per level, "load more" by parent). Soft delete keeps the tree intact; the visible test is the same fact as G's `liveInSubtree` counter (maintained on write so reads are O(1)). Counts on post cards are eventually consistent counters. Hot post: cache the thread page at the CDN for anonymous readers, rate-limit votes per user, and shed the long tail of deep replies. G detail: snapshots are immutable records, state lives in private mutable nodes behind one lock; voting is a SET (compare with the old vote) so retries are idempotent; at scale shard locks by post id, and move to optimistic versioning per comment if contention on a single hot comment dominates.
- **F2:** keep the bytes off the API servers: the client asks for a session (`POST /uploads` -> id, chunk size, pre-signed multipart URLs), uploads parts directly to the object store, the server records part ETags/checksums (idempotent `PUT part n`), `GET /uploads/{id}` returns the received ranges so the client resumes, and `complete` verifies sizes/checksums and atomically flips the state `UPLOADING -> SCANNING -> AVAILABLE` (state machine in a database with conditional updates, not in memory). Dedup by content hash (SHA-256 of the whole file, computed by the client and verified by the server asynchronously) lets "already exists" skip the upload entirely, but an immediate "exists" answer leaks that someone else holds the file: require proof of possession (hash of a challenged byte range) or only dedupe within one user/tenant. Quotas: reserve quota at session creation with an atomic counter and release on abort/expiry, otherwise 100 parallel sessions overshoot it. Abandoned sessions expire through a delayed queue / TTL scan, and the object store's lifecycle rule aborts incomplete multipart uploads (they cost money silently). The scan pipeline reads from a quarantine bucket and the object becomes readable only after promotion; the metadata row is the only source of truth for visibility. Failure modes: a lost `complete` response (make it idempotent by session id), chunk corruption (per-part checksum header), clock skew on URL expiry (short-lived URLs, refreshable by `GET /uploads/{id}/urls`), regional outage (sessions pinned to a region, resume only there).
- **H1:** rules behind each result: JLS 12.4/12.5 (superclass initialised and its constructor body run before the subclass's instance initialisers and field initialisers, so an overridden method called from `Base()` sees default values: `name=null`, but the `final int size = 7` constant variable is inlined and already visible; the static initialiser runs once per class, here `Base.static` is logged before the `clear()`), 5.1.7/5.6 and 15.25 (boxing, the `Integer` cache covers -128..127 only; `Long.equals(Integer)` is false; in `cond ? 1 : 2.0` binary numeric promotion makes the result a double; a `char`-typed operand with an `int` constant that fits in `char` yields `char`, with a non-constant `int` it yields `int`; unboxing a null in a ternary throws NPE), 14.20.2 (a `return` in `finally` replaces the result and an exception, `x = 99` after `return x` does not change the returned value but a mutated object is visible, `break` in `finally` discards a pending `return`), 15.12.2 (phase 1 widening without boxing, phase 2 boxing, phase 3 varargs; most specific method; `p(3L, 4)` is `long,int`, and `p((short) 3, 4)` would be ambiguous), 4.12 (`Object.hashCode` contract: mutating a key after insertion strands it in the wrong bucket; a `TreeSet` comparator defines equality, so same-length strings collapse; `LinkedHashMap` in access order moves a key on `get` and on `putIfAbsent` of an existing key), `Objects.hash(1,2,3)` equals `List.of(1,2,3).hashCode()` (31-polynomial) and `"Aa".hashCode() == "BB".hashCode()`, `binarySearch` returns `-(insertionPoint) - 1`, `String.split` drops trailing empty strings unless the limit is negative and `"".split(",")` returns one empty element, `replaceAll` takes a regex.
- **H2:** an object pool is a resource-ownership problem: whoever holds a `Lease` owns the object, `close()` transfers ownership back exactly once (the `open` flag makes it idempotent and protects against a stale lease freeing an object that was meanwhile handed to someone else). Keep the object out of the pool's public API (callers get `Lease.get()`), then invariants stay inside: `inUse <= created <= capacity`. A closed pool must not resurrect objects: late returns are discarded. The lock is held while creating, fine for cheap objects; for slow ones reserve a slot (increment `created` under the lock), create outside, and roll back on exception. Real pools (HikariCP, Apache Commons Pool) add blocking acquire with timeout (`Condition`/`Semaphore`), validation on borrow, idle eviction and leak detection (a lease that was never closed, found via `Cleaner`/stack trace capture); pooling is only worth it when creation is expensive or the resource is scarce (connections, buffers), otherwise allocation plus GC is cheaper and simpler. With virtual threads, prefer a `Semaphore` to bound concurrency and avoid pinning inside `synchronized` around blocking calls.
