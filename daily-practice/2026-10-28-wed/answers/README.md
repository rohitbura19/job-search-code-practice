B1 paper answers: (a) `takeWhile` -> `[1, 2]`, `filter(x < 3)` -> `[1, 2, 1]`; (b) `IllegalStateException: Duplicate key ...`, use the three-argument `toMap(k, v, mergeFn)`; (c) `limit(5)` -> `[1, 2, 4, 8, 16]`, `takeWhile(x < 20)` on the infinite stream -> `[1, 2, 4, 8, 16]` (it stops at the first failure; without a short-circuit op the stream never ends); (d) `counting()` is `summingLong(e -> 1L)`; (e) `IllegalStateException: stream has already been operated upon or closed`.

H2 paper answers: (a) `for-each` needs a fresh iterator per loop, so `Iterable` is a factory of `Iterator`s and an `Iterator` is a single-use cursor; (b) fail-fast = compare a `modCount` snapshot taken at iterator creation with the collection's current `modCount` on `next()` (best effort, not a guarantee, `hasNext()` does not check); (c) removing from `filter` would have to remove the right underlying element after look-ahead already advanced the source: unsupported is the honest contract; (d) `Spliterator` splits for parallel traversal, reports characteristics (SIZED, ORDERED, SORTED) and has `tryAdvance`/`forEachRemaining`, so streams use it.

F1 / F2 (HLD) anchors.
**F1:** callers emit events through a thin client library: an `eventId` (UUID) for idempotency, actor, action, resource, tenant, outcome, a small context map (IP, request id), never secrets or full payloads (store a reference or a field-level diff with PII hashed); critical actions write synchronously to the audit service (`202` only after the durable append), others go through a local outbox into Kafka partitioned by tenant/shard so the producer never blocks business flow; consumers append to the store in batches: hot tier = time-partitioned columnar/relational tables (or an append-only log in object storage as Parquet) plus a search index keyed by `(tenant, actor)`, `(tenant, resource)` and time; each shard has its own hash chain (`hash = H(prevHash || canonical(event))`), so writers per shard are sequential but shards are parallel, and every N seconds the chain heads are signed and anchored in an external WORM/object-lock bucket or a transparency log, which is what makes tail truncation detectable; `GET /verify` recomputes a range against the anchors; reads need an `audit:read` scope, are themselves audited, and are tenant-scoped; retention by tiering (hot 90 days indexed, then Parquet in cold storage with object lock for 7 years) and a legal-hold flag that suspends deletion; keyset pagination `(time, eventId)` instead of OFFSET; numbers: 20k events/s * 400 B = 8 MB/s, about 700 GB/day raw, about 10x smaller compressed in Parquet; failure modes: Kafka down (outbox buffers), consumer lag (alert on age of oldest unindexed event), duplicate delivery (unique `eventId` per shard), clock skew (server receive time authoritative, caller time kept).
**F2:** devices publish (MQTT or batched HTTPS, mutual TLS or device tokens) to a gateway tier that authenticates, rate limits per device, and writes to Kafka keyed by `deviceId` (per-device ordering, 200k msgs/s is a modest partition count); the point carries a device timestamp, a receive timestamp and a sequence number, writes are idempotent on `(deviceId, ts)`; a stream processor (Flink/Kafka Streams) keeps per-device state for the alert path (threshold with hysteresis and a hold time, so 30 s latency without flapping) and computes 1-minute rollups with event-time windows and an allowed lateness; raw points go to a time-series or columnar store partitioned by day and clustered by device (compressed delta-of-delta/gorilla encoding gets 100 B/point down to a few bytes), TTL 24 h-7 d for raw, 90 d for 1-minute rollups, 3 y for 1-hour rollups; rollups store `count, sum, min, max` (and optionally a sketch for percentiles) because averages of averages are wrong, and are idempotent upserts by `(device, bucket)`; late data (two days late) is accepted into the raw table and triggers a recompute of only the affected buckets (a compaction/backfill job reading the dead-letter or late topic), while alerts ignore anything older than the lateness bound; the query API picks the resolution from the range (max about 1000 points per chart), caches recent windows, and fans out by device partition; cardinality is controlled by keeping `deviceId` as a key, not a tag, and by a fixed metric schema; backpressure: gateway answers 429 with Retry-After, devices buffer locally with a bounded ring and send in batches on reconnect.
