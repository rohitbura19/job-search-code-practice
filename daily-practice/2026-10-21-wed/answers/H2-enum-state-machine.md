Because `on` is `abstract`, a constant without a body does not compile: the compiler enforces that every state defines its transitions, which a `switch` in a service cannot do (a missing case just falls to `default`).

Persisting `ordinal()` ties stored data to the source order: inserting a constant in the middle, or reordering, silently changes the meaning of every stored row, so persist the `name()` (`@Enumerated(EnumType.STRING)`, as in the 18 Oct entity) or an explicit stable code field plus a lookup map. `EnumSet`/`EnumMap` use the ordinal internally, which is fine because they never leave memory.

- Verified on the state machine: all 30 (state, event) pairs return a non-null state, and flattening it to a table shows `CHARGING` reacts to `STOP -> FINISHING`, `PLUG_OUT -> AVAILABLE` and `FAULT -> FAULTED` only (`{STOP=FINISHING, PLUG_OUT=AVAILABLE, FAULT=FAULTED}`), which is the data-driven view of the same behaviour.
- Design comparison: (a) behaviour on the constant keeps the knowledge in one place and the compiler forces completeness per state, but adding an EVENT touches every constant; (b) a service `switch` is easy to read but nothing forces new states to be handled and the logic leaks to wherever the switch is repeated; (c) a transition table is data: it can be loaded from configuration, printed, and checked for unreachable states, at the cost of losing per-state code; (d) sealed interface + records when states carry data (`Charging(sessionId, since)`, `Faulted(code)`) and the `switch` is exhaustive over the sealed set (the 18 Oct sealed-types lesson). Choose (a) for a small closed set with behaviour, (c) when the rules change often or must be audited, (d) when the states have different shapes.
- Also say: an enum can implement an interface (strategy per constant: `PricingRule`), can hold a lambda field (`Comparator`), is implicitly `final` unless it has constant bodies, cannot be instantiated with `new`, and works in `switch` (and an arrow `switch` expression over an enum is exhaustive without `default` when all constants are covered). An enum is the right type for a CLOSED set of values known at compile time; a database table is the right home for a set that changes at run time.
