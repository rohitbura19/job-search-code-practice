# Answers: F1 and F2 (HLD)

(Spoilers.)

**Reference — F1**
```
Status sources (charger OCPP StatusNotification, heartbeat, roaming feed) --> Kinesis/SQS (key = connectorId) --> Status Aggregator
   debounce (ignore flaps shorter than ~10 s), TTL (no heartbeat for 3 intervals => UNKNOWN), derive station_status {free, total, bestFreeKw, updatedAt}
   --> status table (DynamoDB: key = stationId)  --> change fan-out (SNS -> one SQS queue per API pod group, or a poll of "changed since t" every 5 s)
API pods (stateless) hold IN MEMORY:  static index (stations by grid cell, ~6 MB, reloaded when the catalogue version changes)  +  live status map (~10 MB, updated from the fan-out)
App --GET /stations?lat=&lon=&radiusKm=&k=&minKw=&connector=&freeOnly=--> API pod: GeoIndex.nearby(...) with the filter, joined with the in-memory status (see G) -> 200 in a few ms
App --GET /map/tiles/{z}/{x}/{y}?filter=--> CDN (TTL 15 s) --> API pod: pins (zoom >= 13) or cluster counts (zoom < 13, precomputed per cell by the aggregator)
Open map --WebSocket/SSE subscribe(cellIds)--> push {stationId, status} only for the visible cells
Static catalogue: Postgres (PostGIS optional) = source of truth, edited by ops/CPO feeds --> outbox --> catalogue snapshot (S3, versioned) --> pods reload
```
- **Numbers decide the design.** 60k stations x about 100 bytes is about 6 MB; 150k connector states x about 60 bytes is about 10 MB. The whole index and the live state fit in the memory of EVERY pod, so a search needs no database or cache call at all. 5k searches/s over, say, 20 pods is 250/s each of a microsecond-to-millisecond in-memory operation. The expensive part is keeping 20 copies fresh, and 250 to 1,000 status changes a second is small enough to broadcast to all of them. That is the main sentence of the answer; a "database with a geo index plus a cache" also works but is far more machinery for this size.
- **Spatial index.** A uniform grid over latitude/longitude (G), geohash prefixes, S2 or H3 cells all do the same thing: turn "within r km" into "look in these few cells, then measure the exact distance". Cell size is chosen to match the typical search radius (a few kilometres). A cell lookup returns candidates; the exact haversine distance, the filters and a top-k heap finish the job. At scale or with polygons, PostGIS `ST_DWithin` + GiST index is the database-side equivalent.
- **Dynamic state kept out of the static index.** A status change must not rebuild or touch the index; the filter reads the live status map at query time (G). The catalogue changes a few times a day; the status map changes hundreds of times a second.
- **Derived station status.** The map pin needs "3 of 4 free, best 150 kW": compute it once when a connector changes and store it, instead of recomputing per request. Clusters at low zoom are counts per cell per zoom level, maintained incrementally by the aggregator.
- **Trust.** Never show FREE on a stale signal. Each state carries `updatedAt`; no heartbeat within three intervals becomes UNKNOWN (greyed out, still on the map, shown after the confirmed-free ones); a flap shorter than a debounce window is ignored; third-party feeds with known lag are shown as "last confirmed 2 min ago". The measure of quality is the ARRIVAL MISMATCH rate: the driver arrived (navigation ended near the station) and the state they saw was wrong.
- **Push versus poll.** Polling tiles every 15 s is simple, cacheable at the CDN, and wasteful when nothing changes; a WebSocket/SSE subscription by cell sends only changes for the visible cells (a few KB), but needs connection fan-out infrastructure and reconnect handling. Start with short-TTL tiles; add push for the "I'm navigating to this charger" screen only, where freshness matters most.
- **Hot cities.** 30% of searches fall in a few cities. In-memory lookups are cheap, so the load is CPU on the pods in that region: shard the traffic by region at the load balancer, cache tile responses at the CDN keyed by (tile, filter hash), and keep per-pod memory identical (the catalogue is small).
- **The honest edge cases.** Driver in a tunnel (the last location is old: ask the client for the accuracy and age), search near the antimeridian or a pole (G handles the wrap), a charger moved or decommissioned (catalogue version, a `retiredAt` field), a very large radius (G: do not scan millions of empty cells).
- **Failure modes.** Status stream lagging: the pods keep serving the last known state, the TTL turns old entries into UNKNOWN, an alarm fires on the age of the newest event per region. Catalogue reload fails: keep the previous snapshot (never serve an empty index). A pod restarts: it loads the snapshot and the current status table before it joins the load balancer (readiness). A bad third-party feed: quarantine that operator, do not poison the map.
- **Metrics.** Search latency p50/p99, status staleness (age of the newest event, per region), share of connectors UNKNOWN, arrival mismatch rate, zero-result searches (a catalogue or filter problem), tile cache hit ratio, pod memory and reload time, push fan-out lag.

**Reference — F2**
```
Phone: SQLite  (job, field values, photo metadata)  +  op_log (opId, jobId, path, value, deviceId, deviceSeq, hlc, baseRev, schemaVersion)  +  photo_queue
   edit  -> write the field locally AND append an op, in one local transaction      (the UI reads local data only: instant, works offline)
Sync (on connectivity change, app foreground, every 15 min via the OS scheduler; backoff + jitter):
   POST /jobs/{id}/ops:batch  {deviceId, ops[<=100]}   --> server applies in order, idempotent by opId  --> per-op result {opId, accepted|rejected(reason)}, new serverRev
   GET  /jobs/{id}/changes?sinceRev=n                  --> ops by others (supervisor, helper) in server order       --> merged into local data
Photos: POST /jobs/{id}/photos {photoId, sha256, size}  --> presigned S3 multipart URLs --> background resumable upload --> S3 event --> verify checksum, thumbnail (Lambda), mark photo READY
Server: ops table (jobId, serverRev, opId unique, ...)  + materialized current state (jobs table, JSON)   [DynamoDB: PK = jobId, SK = serverRev;  or Postgres rows]
Submit: op "submit" is server-authoritative: validates required fields/photos, sets state SUBMITTED, locks; later ops are rejected with a clear reason
```
- **Log, do not overwrite.** Saving "the form" loses information when two devices edit or a sync is retried. An operation log gives replay (resend the unacknowledged ops until the server says so), idempotency (`opId` is a UUID made on the phone; the server keeps a unique index and answers a repeat with the stored result), ordering (per device sequence), and an audit trail for free. Coalesce before sending: ten edits to the same field can be one op.
- **Which clock.** The server assigns a monotonically increasing `serverRev` per job: that is the real order. For merging offline edits made at the same time, use a hybrid logical clock (`wall time + counter + deviceId`) as the tie-breaker, not the raw phone time (phones are wrong by minutes). Limit trust: reject ops with an HLC far in the future.
- **Conflict rules by data type.** A scalar field (a reading, a tick box): last writer wins by (HLC, deviceId), and the loser's value stays in the log, so the supervisor can see "changed by two people". Collections (photos, notes): add-only set union, where a delete is a tombstone. The job state (draft -> submitted -> locked): server-authoritative state machine; an edit that arrives after the lock is rejected and shown to the installer as "this job was already submitted". This is a small, deliberate CRDT-style design: per-field registers plus an add-only set, without the machinery of a general CRDT library.
- **Photos on their own path.** 3 MB photos must not ride in the JSON batch. Register the photo (metadata op, so the checklist can show a placeholder and sync immediately), then upload the bytes with a resumable multipart upload to S3 in the background; a retry sends only the missing parts. The `sha256` lets the server verify the upload and de-duplicate; EXIF location/time can be stripped or kept deliberately (privacy). Compress on the phone (about 3 MB is already a compressed image: resizing to 2048 px saves more). Upload on Wi-Fi first, mobile data on request.
- **Tokens and time offline.** The access token expires while offline: keep a long-lived refresh token in the secure store, refresh at sync time; a 401 that cannot be refreshed puts the app in a "sign in to sync" state WITHOUT touching local data. Never wipe local data on logout while unsynced ops exist: warn, offer to sync first, or export.
- **Versions.** Ops carry `schemaVersion`; the server upgrades an old op to the current shape (a migration function) and supports the last N versions; unknown fields are kept, not dropped. A forced-update gate is the last resort.
- **Idempotency and partial failure.** A batch can fail halfway (timeout after the server applied 60 of 100). The client resends the SAME ops; the server answers the first 60 from the unique `opId` index and applies the rest. The client marks an op done only when the response lists it.
- **Security and privacy.** Local database encrypted at rest (platform keystore); customer name, address, photos and signature are personal data: restrict who can read a job (installer company), expire presigned URLs in minutes, no personal data in logs, remote wipe on device revoke after a final sync attempt.
- **Failure modes.** Phone lost before sync: the work is gone; reduce the window by syncing metadata ops early and photos on Wi-Fi, and tell the installer the unsynced count on the home screen. Clock far off: HLC tie-break plus server order. Helper and installer tick the same item: LWW, shown in review. S3 upload never completes: the job cannot be submitted (required photo missing), with a clear message.
- **Metrics.** Age of the oldest unsynced op per device (p95), sync success rate and retry count, conflict rate per field, photo time-to-complete, jobs submitted with missing photos, batch rejection reasons, share of app versions in use, storage growth per day.

### Principal-level discussion: make F1 more efficient
1. **Where does the CPU go?** With everything in memory, the time is in the distance computation and in scanning candidates. Measure candidates examined per query (in G: about 320 for a 3 km radius in a dense city, 7 on average for a 5 km radius over a country-sized spread) and tune the cell size; prefilter by `connector`/`minKw` with a per-cell bitmask before the haversine.
2. **Large radius and empty cells.** A grid scan costs the number of CELLS in the box, not the number of chargers: G measured 25.9 million cell lookups for a 20,000 km radius. Cap the radius (the product never needs more than about 100 km), or switch to iterating the non-empty cells when the box has more cells than the index has entries.
3. **Tiles and clusters.** Precompute cluster counts per cell per zoom and cache tiles at the CDN with a 15 s TTL; a status change only invalidates by TTL. What does it save (most map pans become cache hits) and what does it cost (up to 15 s of staleness, which is within the 30 s budget)?
4. **Delta push.** Replace "every pod holds all 150k states" by "every pod holds its region's states" when the fleet grows 10x: shard by geo prefix at the load balancer and fan out per region. When is replicating everything still the simpler and cheaper answer (at this size, always)?
5. **10x.** 1.5M connectors: the index is 100 MB per pod, still fine; the status stream is 10k events/s, which a partitioned stream and per-region consumers handle. Where would you first introduce a real spatial database (polygons, "along my route" queries, historical analytics) and keep the in-memory index as the hot path?

### Principal-level discussion: make F2 more efficient
1. **Send less.** Coalesce ops per field before the sync, compress the batch, send only the fields that changed since the last acknowledged revision. What does a typical job cost in bytes if the photos are excluded (a few KB), and what dominates (the photos)?
2. **Photo pipeline cost.** 150 GB a day is about 4.5 TB a month: S3 lifecycle (Standard to an infrequent-access tier after 30 days), thumbnails generated once and served instead of originals, de-duplication by hash, and retention rules agreed with legal. What is the cheapest correct way to let the supervisor view a photo (a short-lived presigned URL of the thumbnail)?
3. **Real CRDT or not.** When would per-field LWW plus add-only sets stop being enough (collaborative editing of a long free-text note, reorderable lists)? What would you adopt then, and why not adopt it on day one?
4. **Sync storms.** 20k phones regain signal after an outage in the same minute. Jitter on the client, a server-side rate limit that returns `429 Retry-After`, small batches, and photo uploads that can be paused. Which of these is the first line of defence?
5. **10x.** 50k jobs a day: the ops table is write-heavy and keyed by job, so it shards naturally; the materialized state is rebuilt from the log if a bug corrupts it. How do you prove a rebuilt state equals the stored one (replay both and compare a hash)?
