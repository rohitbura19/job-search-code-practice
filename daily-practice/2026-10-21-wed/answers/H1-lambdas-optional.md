# Answers: H1-lambdas-optional

(Spoilers. Open only after your attempt.)

**Reference** (all outputs verified by running the code on JDK 21)
- Line 1: `0 1 2 a b`. Each iteration of the loop creates a NEW `j` (a fresh local per iteration) that the lambda captures by value; the enhanced `for` variable `s` is also fresh per iteration. Line 1b does not compile: `local variables referenced from a lambda expression must be final or effectively final` (verified), because the classic loop counter `i` changes. The rule exists because a lambda captures a COPY of the value (the local variable may be dead when the lambda runs, on another thread); allowing mutation would give the illusion of shared state that does not exist.
- Line 2: `2`. The array reference is effectively final, the element is mutable heap state. This is fine on one thread; it is a race in a parallel stream (use `AtomicInteger`/`LongAdder`, or better a reducing collector).
- Line 3: `outer Greeter` then `anon true`. In a lambda `this` is the ENCLOSING instance (a lambda introduces no new scope for `this`), so `this.name` is `outer` and `getClass()` is `Greeter`. In an anonymous class `this` is the anonymous object, `this.name` is its own field, and `getClass().getSimpleName()` is the EMPTY string. A lambda is not an inner class: the compiler generates a private method and an `invokedynamic` call site; the runtime spins a class (named like `H1$$Lambda/0x...`) on first use.
- Line 4: `s::toString` throws `NullPointerException` where the reference is CREATED (the receiver is evaluated immediately and null-checked), while `() -> s.toString()` was created fine and throws only when `get()` is called (verified: `lambda created; NPE at call; NPE at creation of the method reference`).
- Line 5: `first second`. In `holder[0]::toString` the expression `holder[0]` is evaluated ONCE when the reference is created, so it keeps pointing at the first builder; the lambda reads `holder[0]` at each call and sees the second. For `Type::instanceMethod` (unbound), the first argument of the function becomes the receiver (`String::length` is `s -> s.length()`).
- Line 6: prints `expensive ` once (from `orElse`: its argument is evaluated EAGERLY even though the optional has a value), nothing for `orElseGet` (the supplier runs only when empty), then `false`: `map` returning null gives an empty optional. `Optional.of(null)` throws `NullPointerException`; `Optional.empty().get()` throws `NoSuchElementException: No value present` (verified); prefer `orElseThrow()`. `Optional` is a return type for "may be absent"; as a field it is not `Serializable` and wastes memory, as a parameter it forces callers to wrap.
- Line 7: `12 11`. `f.andThen(g)` is `g(f(x))` = (5+1)*2; `f.compose(g)` is `f(g(x))` = 5*2+1. Currying is just nested functions: `Function<Integer, Function<Integer,Integer>> add = x -> y -> x + y` (`add.apply(2).apply(3)` is 5, same as `Integer::sum` as a `BiFunction`).
- Line 8: `Callable Runnable Callable Runnable Callable`. A lambda whose block can only throw is both void- and value-compatible, and when both overloads apply the non-void (`Callable`) one wins; `System.out.println()` returns void so only `Runnable` fits; `() -> "x"` only fits `Callable`; the empty block only `Runnable`; `() -> five()` is an expression statement that is compatible with both and again prefers `Callable`. The consequence: `submit(() -> doWork())` where `doWork()` returns a value runs as a `Callable`, and its exceptions are captured.
- Line 9: `true false` on HotSpot (verified): a non-capturing lambda is created once per call site and reused, a capturing lambda gets a new object per evaluation. This is an implementation detail: never depend on lambda identity, and never use a lambda as a key in a map or a listener you must remove later (keep the reference in a field).
- Line 10: the `IllegalStateException` is stored in the `Future` and thrown only from `fu.get()` as an `ExecutionException` with the original as its cause (verified: `boom via get`). A second task submitted with `submit` and never inspected loses its exception silently (verified: nothing printed). With `execute(Runnable)` the exception goes to the thread's uncaught-exception handler and, in a pool, kills that worker thread (the pool replaces it). Rule: always keep the `Future` and call `get`, or wrap the task body in try/catch and log.
- Line 11: `Comparator.comparing(s -> s.length()).reversed()` does NOT compile (`cannot find symbol: method length()`, verified): in the chain the target type is not propagated to `comparing`, so `s` is inferred as `Object`. Fixes: `Comparator.comparing(String::length).reversed()`, `Comparator.comparing((String s) -> s.length()).reversed()`, or `Comparator.<String, Integer>comparing(s -> s.length()).reversed()`; or use `Comparator.comparingInt(String::length).reversed()`.
- Also say: the functional interfaces to know (`Function`, `BiFunction`, `Supplier`, `Consumer`, `Predicate`, `UnaryOperator`, `BinaryOperator`) and their primitive variants (avoid boxing in hot paths); `Predicate.and/or/negate`; `@FunctionalInterface` (one abstract method, default and static methods allowed); checked exceptions in a lambda need a wrapper (a custom functional interface that throws, or catch and rethrow unchecked); a stream pipeline's lambdas must be non-interfering and stateless.
