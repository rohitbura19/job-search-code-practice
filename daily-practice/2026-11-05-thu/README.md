## Principal-engineer review: follow-ups and how to make each design more efficient

- **A1 / A2:** Product-except-self with division fails on zeros (count them: 0 zeros -> divide, 1 zero -> only that slot is non-zero, 2+ -> all zero) and on overflow; the two-pass prefix/suffix form is the safe default. Rotation by reversal is three passes with perfect cache behaviour; the juggling/cycle-leader variant does n writes but jumps around memory, and `System.arraycopy` into a temp is the pragmatic choice when O(k) extra space is allowed. `pivotIndex` needs `long` because `int` sums overflow; the same prefix-sum idea answers range-sum queries in O(1) after O(n) preprocessing (and 2D with inclusion-exclusion). `strStr`: naive is O(n*m) on `aaaa...b`; KMP (failure function) or Z-algorithm gives O(n+m), Rabin-Karp gives expected O(n+m) and extends to many patterns, Aho-Corasick handles a whole dictionary. Know that `String.indexOf` is intrinsified and fast in practice. `reverseWords` in place on a `char[]`: reverse everything, then each word. Zigzag is a cycle of length `2*rows-2`: each row's indices are computable directly, so no per-row builders are needed.
- **B1:** `flatMap` + `distinct` + `sorted` is a pipeline of stateful ops: `distinct` and `sorted` buffer, so on huge inputs prefer a `TreeSet` filled in a loop. `groupingBy(..., TreeMap::new, downstream)` fixes ordering; sorting once before grouping is O(n log n) while sorting inside each group costs the same but allocates more. `toMap` without a merge function throws on duplicates, and `toMap` with `null` values throws NPE (use `groupingBy` or a loop). `IntSummaryStatistics` computes five numbers in one pass with `long` sum; `summarizingInt` is the collector form (usable as a downstream). `Comparator.nullsLast` must wrap the rating comparator, not the other way round, and `Double` comparisons must use the boxed comparator (`Double.compare` semantics for `NaN` and `-0.0`). Parallel streams are a trap for small lists and for ordered collectors; measure first.
- **C1:** Every "count subarrays with property P" problem becomes "count pairs of equal (or complementary) prefix values". Seed the map with the empty prefix. Use `long` prefixes with `int` inputs. `HashMap<Long,Integer>` boxes: for hot paths sort the prefixes or use a primitive open-addressing map; for the divisible-by-k version an `int[k]` is faster and needs `floorMod`. Negative numbers kill sliding-window solutions (the window is not monotone) which is why the prefix-sum form is the general one; with only positive numbers and "sum = k", two pointers gives O(1) space. Balanced 0/1 generalises to "equal counts of two kinds" and to 2D (max rectangle with sum <= k uses prefix sums over column pairs + a sorted set). Follow-ups: shortest subarray with sum at least K with negatives (monotonic deque over prefixes), maximum size subarray sum equals k, count of range sums in [lo, hi] (merge sort over prefixes or a Fenwick tree).
- **C2:** BFS is shortest path on an unweighted graph; the multi-source trick works because the "super source" connected to all sources by zero-length edges is still unweighted. Process by levels (`size` loop) to count minutes without storing distances; mark visited when you ENQUEUE, not when you dequeue, or states are queued many times. `openLock` is also a good place for bidirectional BFS: expand the smaller frontier from both ends, cutting the search from `b^d` to `2 b^(d/2)`. For weighted edges use Dijkstra, for 0/1 weights a deque (0-1 BFS), and for a good heuristic A*. Memory for 1500x1500 grids: `int[][]` is fine, but `ArrayDeque<int[]>` allocates a million tiny arrays: encode `r * n + c` into an `int` queue (a primitive ring buffer) if profiling shows GC. `nearestZero` has a two-pass DP alternative (top-left then bottom-right sweep) with no queue at all.
- **D1:** The partition invariant: `i + j = (m + n + 1) / 2`, every element left of both cuts is <= every element right of both cuts, which only needs `a[i-1] <= b[j]` and `b[j-1] <= a[i]`. Searching the shorter array bounds `j` to a valid range and gives O(log min). Use sentinels (`+-infinity`, here `long` extremes) instead of special cases; average in `double`/`long` to avoid overflow. Generalisation: k-th element of two sorted arrays, then of k sorted arrays (heap, or binary search on the value with counting: O(k log(range) log n)). Streaming median uses two heaps (O(log n) insert, O(1) median) and an order-statistics tree or a Fenwick tree when deletions are needed; for approximate quantiles on huge streams use t-digest or a Greenwald-Khanna sketch.
- **E:** The two classic Kafka consumer failure modes are lost and duplicated work. With at-least-once delivery (commit after processing) a crash replays messages, so the handler must be idempotent: here a `ProcessedEvent` row with the event id as primary key is written in the SAME transaction as the state change; a replay hits `existsById` (or the unique constraint under a race: two consumers in one group never share a partition, but a rebalance can overlap, so also catch `DataIntegrityViolationException` and treat it as "already done"). Forward-only status makes out-of-order events harmless; keying messages by `orderId` keeps per-order order within a partition. The producer side has the dual-write problem: `save` then `send` inside one transaction can leave the DB committed and the message lost (crash) or the message sent and the DB rolled back. Fix with the **transactional outbox** (write the event to an `outbox` table in the same transaction, a relay publishes it and marks it sent; consumers dedupe) or, for simple cases, publish after commit with `@TransactionalEventListener(AFTER_COMMIT)` and accept the small loss window. Check the `send` future (`whenComplete`) and set `acks=all`, `enable.idempotence=true`, `retries`, `delivery.timeout.ms` so transient broker errors do not lose data or reorder. Poison messages: `DefaultErrorHandler` with `FixedBackOff`/exponential backoff plus `DeadLetterPublishingRecoverer` (dead-letter topic), and an `ErrorHandlingDeserializer` so a bad payload does not block the partition forever. Consumer lag, rebalance frequency and `max.poll.interval.ms` (slow handlers cause rebalances) are what you monitor. Test levels: slice tests with a mocked template (as here) for logic, `@EmbeddedKafka` or Testcontainers for one wiring test. `Page` JSON is not a stable contract: return your own record. `(:status is null or ...)` is simple but can defeat indexes: switch to Specifications when filters grow, and use keyset pagination for deep pages.
- **F1 / G:** Two paths: PREVIEW is read-only, cacheable, and may be slightly wrong; REDEEM is the exact, rare, transactional one. Code definitions are small and immutable per version: cache them in every service instance (invalidate by version/pub-sub). The hard part is the global counter on a hot code (50 k/s on one row). Options: a single Redis key with `INCR`/Lua (check total and per-user in one atomic script, `SADD`/`HSETNX` for the per-user and the order-id idempotency key), sharded counters (N sub-budgets, a shard hands out its slice; a little unused budget is stranded at the end, which is fine for marketing but not for a legal limit), or pre-allocated tokens in a queue. Reserve first, confirm when the order is paid, expire the reservation on TTL (so abandoned checkouts do not burn the limit) - this is a two-phase redemption and `release` is the cancel path. Idempotency key = order id stored with the reservation; retries return the stored result. Durable truth is a relational table `(code, order_id, user_id, status)` with unique `(code, order_id)` and a unique `(code, user_id)` when the per-user limit is 1; Redis is a fast gate rebuilt from it after a failure. Single-use bulk codes: store a hash of the code (not the plain text), generate with a CSPRNG and enough entropy (>= 60 bits) so guessing is infeasible, and rate-limit validation per user/IP/device (a flash-sale code leaked to a deal site is the real abuse). Failure mode: if the coupon service is down, checkout should fail OPEN for preview (hide the field) but fail CLOSED for redeem of limited codes, or accept the order with a "pending discount" reconciled later; decide with the business. LLD: per-coupon lock (or `AtomicInteger` CAS loop) gives atomic check-and-consume without a global lock; `computeIfAbsent` runs its function under a bin lock and must be short and side-effect free, so it is the wrong place for business logic; `Clock` injection makes validity windows testable; money in `long` cents with explicit rounding (floor) and a cap by subtotal; stacking rules would be a `Rule`/`Discountable` strategy list with an explicit ordering policy (percent before flat or the reverse changes the total).
- **F2:** The relationship table `likes(post_id, user_id, type, created_at)` with primary key `(post_id, user_id)` is the source of truth and gives idempotency and "did I like it" for free; the count is a denormalised, derived number. Never `count(*)` on read. Write path: like = upsert into the relationship store (partitioned by post id; Cassandra/DynamoDB/sharded MySQL), emit an event to Kafka keyed by post id; a counter service aggregates events and applies batched increments (`+37` every 100 ms) to the counter store, so a celebrity post sees 10 writes/s instead of 50 k/s. For a single hot key shard the counter (`post:123:shard:0..15`, random shard on write, sum on read, cache the sum for a second). Reads: counts live in Redis (hash per post, type -> count), the feed does one `MGET` for 20 posts; the viewer's own state for a page is a batched point lookup (or a per-user bloom filter/bitmap of recent likes). Read-your-writes: the client applies the optimistic +1 locally and the API returns the new state; the server can also keep a short-lived per-user overlay. Eventual consistency is fine for counts, but the periodic reconciliation job (recount from the relationship table for popular posts, sample the rest) repairs drift from lost or duplicated events, which is why events need ids and the aggregator dedupes. "Who liked": the table clustered by `(post_id, created_at desc)` with keyset pagination; for celebrities cap how deep the list goes. Unlike is a delete/tombstone plus a `-1`. Rate-limit per user to stop scripted like bursts; fake-engagement detection is a separate async pipeline. Cost note: 100 k writes/s at ~100 bytes is about 10 MB/s of relationship rows (~800 GB/day): TTL or tier cold posts.
- **H1:** rules behind each result: JLS 12.4/12.5 (class initialisation once, instance initialisation order: super constructor first, field initialisers and instance blocks in textual order, then the constructor body; an overridden method called from a constructor sees default values), 14.20.2 (finally: the return value is computed before finally runs, but a `return` in finally replaces it; `continue` and `throw` still run finally), 5.1.7 and `Integer.valueOf` (cache -128..127), `Long.equals(Integer)` is false (type check), 15.25 (conditional operand typing: numeric promotion, constant `int` that fits `char` keeps `char`), 15.26.2 (compound assignment has an implicit cast), 5.1.3 (narrowing keeps the low bits), `List.remove(int)` vs `remove(Object)`, `Arrays.asList` (fixed-size write-through view), `Collections.unmodifiableList` (view) vs `List.copyOf` (copy), `HashSet` with a mutated key (bucket by old hash), JLS 3.10.5/15.29 (constant expressions are interned, `final` local with a constant initialiser is a constant variable), `StringBuilder` does not override `equals`, `String.split` Javadoc (trailing empties removed), JLS 15.12.2 (overload phases: strict without boxing, loose with boxing, then varargs; most specific method; static type decides).
- **H2:** Sealed interfaces + records + `switch` patterns are Java's algebraic data types: the closed set of cases is checked at compile time, so adding `Sub` breaks every non-exhaustive `switch` (no `default`, or you lose that safety). Compared with Visitor, you give up the ability to add new types without touching operations but gain ordinary methods and no double dispatch. Records give `equals`/`hashCode`/`toString` and make trees directly comparable in tests; remember a record is shallowly immutable (a `List` component needs a defensive copy in the compact constructor). `simplify` as a single bottom-up pass is correct only because each rule outputs an already-simplified tree; add rules (distribution, `x + x -> 2*x`) and you need a fixed-point loop or a rewrite engine, plus a termination argument. Deep trees (10^5 nested `Add`) overflow the stack: convert to an explicit stack or a post-order iterator, and consider hash-consing (interning equal subtrees) for large expression DAGs. Property-based testing, as in `simplifyPreservesValueOnRandomTrees`, is the right tool for rewrite systems: random trees, evaluate before and after, assert idempotence.
