## Principal-engineer review: follow-ups and how to make each design more efficient

- **A1 / A2:** `sortedSquares` is the merge step of two sorted runs (negatives reversed, non-negatives); with `int` the square of `Integer.MIN_VALUE` overflows, so widen to `long` first. `intersect`: sort both and walk two pointers for O(1) extra space when memory matters, or hash the smaller side; for arrays too big for memory use an external sort or a Bloom filter pre-pass. `rotateRight` by three reversals is cache-friendly; the cycle-leader method does n moves but jumps around memory (gcd(n, k) cycles). `compress` must write behind the read pointer, which is why the run length is computed before anything is overwritten; in Java 21 with `String` input use a `StringBuilder`. IPv4: parse by hand (no regex backtracking, no `Integer.parseInt` surprises with `+`/whitespace) and mention IPv6 and `InetAddress` pitfalls (it may do DNS for names). `addStrings`: the same loop with base 10^9 chunks cuts the work 9x; BigInteger switches to Karatsuba/Toom-Cook for multiplication only.
- **B1:** Each method is one collector chain. `alwaysAbove` keeps only a per-sensor minimum (O(sensors) memory) instead of materialising readings; `topValuesPerSite` sorts whole groups, a bounded heap per site (size n) is O(m log n) and safer for hot sites. `busiestSite` is `counting()` then a max with a tie-break; the comparator must break ties on the key explicitly because `HashMap` order is unspecified. `averagePerSensor` should use `summarizingInt`/`averagingInt` once; averaging averages is a classic bug. For unbounded data this belongs in a stream processor (per-key state with windows), not a list.
- **C1:** 2-colouring by BFS is O(V + E) and a failed edge gives an odd cycle witness (keep parents to print it); union-find with a parity bit handles edges arriving online. Safe nodes by reversed-graph Kahn is O(V + E) with no recursion; the DFS three-colour variant is equivalent but needs an explicit stack for 200k-deep chains. The safe set is the complement of "nodes that can reach a cycle", which is the same fact as SCC condensation: for repeated queries compute SCCs once (Tarjan/Kosaraju, iterative). `possibleBipartition` with duplicate pairs is harmless because colouring is idempotent; with weighted "same/different" constraints use union-find with parity.
- **C2:** `maximalSquare` is the standard `min(left, up, diag) + 1` with one row and a saved diagonal; the O(c) memory trick requires the saved `diag` before overwriting `dp[j]`. For the maximal *rectangle* use D1. Stock with cooldown: three states because a sale today forbids a buy tomorrow; the same shape handles "k transactions" (add a dimension) and "fee per trade". `numSquares` is O(n sqrt n) DP; BFS over remainders is faster in practice for one n, and Lagrange's four-square theorem plus Legendre's three-square test answers in O(sqrt n) (answer 4 iff n = 4^a(8b+7)); use it only if the interviewer asks for the optimum.
- **D1:** Monotonic stack with a sentinel pass: each bar is pushed and popped once, O(n) time, O(n) space; the int-array stack avoids boxing (a 10^6 `ArrayDeque<Integer>` allocates a lot). Alternatives: divide and conquer on the minimum with a sparse table (O(n log n)), or left/right nearest-smaller arrays computed in two passes (same O(n), easier to explain, twice the memory). `long` is mandatory: 10^6 bars of 10^9 is 10^15. For `maximalRectangle` the row-by-row heights array makes it O(rows * cols); for dynamic updates you would need a segment tree storing (min, best).
- **E:** `@ManyToOne(fetch = LAZY)` yields a proxy: reading the id is free, any other getter needs an open session; the entity graph turns the lazy association into a join in this query only, which is the cure for the N+1 problem (batch fetching `default_batch_fetch_size` or a projection are the alternatives; never switch the mapping to EAGER globally). The interface projection (`PlanCount`) selects only two columns and avoids loading entities; its aliases must match the getter names. `existsBy` compiles to `select ... limit 1`, cheaper than `count`. A unique constraint is the only real guard against the get-or-create race (two requests both see no account): catch `DataIntegrityViolationException` and retry or return 409, never rely on `findByEmail` + `save` alone; here the "one ACTIVE subscription per account" rule is also check-then-act, so add a partial unique index (`where status = 'ACTIVE'`, in Postgres) or lock the account row (`@Lock(PESSIMISTIC_WRITE)`) in production. `@ConfigurationProperties` records are immutable and validated at startup (fail fast); read `Clock` and properties from beans so tests need no sleeps. `ResponseEntityExceptionHandler` already gives RFC 7807 responses for validation errors; the DELETE returns 204 and is idempotent so client retries are safe. Add `Idempotency-Key` for POST (see 2026-11-02 wallet) and an ETag/`@Version` for the PUT.
- **F1 / G:** Store events per attendee (user-partitioned): each attendee row points to a shared event record, so a week view is one range scan `(user, start)` and free/busy is a merge of sorted lists; the cost is write amplification per invite (fine: events are small, invites few). Recurring events are stored as a rule (RRULE + timezone id + exceptions) and expanded lazily for the requested window; store occurrences in UTC but recurrence in the organizer's zone, otherwise DST breaks "every Monday 9:00". Conflict check = the two-neighbour lookup on a sorted structure (G); across shards the schedule is a small saga: reserve on each attendee shard in a fixed order and compensate on conflict (or make the organiser's partition the single writer and treat attendee calendars as eventually consistent, since a double booking of an attendee is a warning, not a correctness bug). Free/busy for 50 attendees: fan-out read of busy intervals only (no titles: privacy), cache per user per day, merge in the caller; precompute "next 14 days busy bitmaps" for hot users. Reminders: a delayed-queue/timer wheel keyed by fire time, sharded by user. G detail: half-open ranges make back-to-back meetings legal, `TreeMap.floorEntry` and the first key after start are the only two candidates because a user's events never overlap, and validate-then-mutate gives atomicity without rollback; multi-threaded use needs per-user locks acquired in sorted order.
- **F2:** Pings go over a persistent connection (MQTT/WebSocket/gRPC stream) with batching and delta encoding; the ingest service writes the latest position to an in-memory store keyed by courier (Redis/Aerospike, TTL), appends history to Kafka for ETA models and analytics, and never makes the phone wait on a database. Fan-out: one topic per order; the edge (WebSocket gateway) subscribes only while a customer is watching, throttles to about 1 update per 2-3 s, drops stale frames (latest wins) and sends nothing when the courier is stationary. 3M watchers x 0.4 updates/s = about 1.2M msgs/s: shard gateways by order id, use a pub/sub tier with consistent hashing. ETA is recomputed on meaningful movement or traffic change, not per ping, with map-matching to snap noisy GPS to roads; a cheap client-side interpolation hides gaps. Geo-index (H3/S2 cells) for dispatch, not for tracking. Privacy and cost: retain precise trails briefly, purge or coarsen after delivery, region-pin the data; degrade gracefully (poll every 10 s) when the realtime tier is down.
- **H1:** rules behind each result: JLS 8.3 (fields are resolved on the static type, they are hidden not overridden), 8.4.8 (static methods are hidden), 15.12 (overload chosen at compile time from the static argument type, the override picked at run time from the receiver), 3.10.5/15.29 (a `final` String local initialised with a constant is a constant expression and is pooled; `j + "va"` with a non-final `j` is computed at run time), `i++ + ++i` evaluates left to right, a `byte` shift is done on the promoted `int` (`>>>` on a negative byte yields a big int that the cast truncates), `Math.abs(Integer.MIN_VALUE)` is still negative, `Math.round` rounds half up (towards positive infinity), `x += 300` on a byte has an implicit narrowing cast; streams are pull-based per element so `peek` interleaves, `sorted` is a full barrier, `limit` short-circuits only after the barrier, and since JDK 9 `count()` skips the pipeline when the size is known; 14.20.3.1 (resources close in reverse order, close exceptions are suppressed onto the body exception, but surface as the exception when the body completed normally); `List.remove(int)` vs `remove(Object)`, `Arrays.asList` is a fixed-size write-through view, `subList` is a view invalidated by structural changes of the parent, `unmodifiableList` is a read-only view not a copy, `List.of(...).contains(null)` throws, `HashMap` permits one null key. The count() line depends on JDK 9+ behaviour.
- **H2:** A value object has no identity, no setters, validates in its factory and defines equality by value; storing minor units in a `long` makes arithmetic exact and overflow detectable (`Math.addExact`), while `double` cannot represent 0.10 and `BigDecimal` fields invite scale bugs in `equals`. Allocation must conserve the total: truncate towards zero, then hand out the leftover one unit at a time (never to zero-ratio parts); `BigInteger` in the proportional step avoids overflow of `amount * ratio` for large values. Interning, a `Currency` cache or a record are possible, but records expose the constructor, so a final class with factories keeps invariants (a `record` with a compact constructor is equally valid if the canonical constructor is the validating one). `Comparable` is only meaningful within one currency; sorting a mixed list should fail loudly. Cross-currency conversion belongs in a service with dated rates, not in the value type. Serialization: ship `{minor, currency}` or a decimal string, never a floating point number.
