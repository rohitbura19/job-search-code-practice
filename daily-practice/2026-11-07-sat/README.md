## Principal-engineer review: follow-ups and how to make each design more efficient

- **A1 / A2:** Stairs is Fibonacci: a matrix power or fast doubling gives O(log n) and, with `BigInteger` or a modulus, handles huge n; variants: steps in `{1,3,5}` (coin-change counting), forbidden steps, cost with k-step jumps (monotonic deque). Rolling variables beat arrays: memory O(1) and cache friendly. Linked lists: the dummy head and the gap-n runner are the two reusable tricks; ask for "remove all nodes with value v", "merge k lists" (heap, O(N log k), or pairwise divide and conquer), "detect the cycle start", "reorder list" (middle + reverse + interleave, all O(1) space). In production a linked list is rarely the right structure (pointer chasing, poor cache locality): prefer `ArrayList`/`ArrayDeque` unless you need O(1) splice with stable iterators.
- **B1:** One traversal per method; compare `groupingBy(..., TreeMap::new, downstream)` with sorting afterwards. `topTags` sorts all distinct tags: for huge cardinality use a bounded min-heap of size n (O(m log n)) or an approximate sketch (Count-Min + heap) when exact counts are unnecessary. `maxBy` with a composite comparator makes ties explicit, which is what makes results reproducible across runs and JDKs. Averages of cents as `double` hide rounding: for money keep `long` sums and counts and divide once. `partitioningBy` always has both keys; `groupingBy` never creates empty groups, so use partition when the empty side matters. Parallel streams only for large CPU-bound work with associative, stateless accumulators.
- **C1:** Preorder+inorder needs distinct values (otherwise the split is ambiguous); inorder+postorder is symmetric; preorder alone suffices for a BST (insert in order, or one pass with bounds, O(n)). The iterative stack version is the same algorithm as the recursive one with an explicit "pending ancestors" stack and the inorder pointer saying when a left spine ends. For the codec, level-order text keeps LeetCode compatibility and is easy to read; for a compact wire format use preorder with null markers or a bit-packed shape plus a value array; for evolving schemas, protobuf with a node list and child indexes. Parsing untrusted input needs limits (max nodes, max depth, integer range) and error handling instead of `NumberFormatException` leaking out. `ArrayDeque` forbids `null`: a classic BFS bug.
- **C2:** Expand-around-centre is O(n^2) and O(1) space, perfectly fine for n <= 5000; Manacher is O(n) via mirrored radii; the DP table is O(n^2) memory and only worth it when you need all palindromic substrings (count them, answer range queries). Suffix automaton/suffix array + LCP solves "longest repeated" variants. Target sum is subset-sum counting: O(n * P) with P the derived target (pseudo-polynomial; NP-hard in the bit length); iterating the capacity downward is what makes the 1-D array a 0/1 (not unbounded) knapsack. Alternatives: memoised recursion over `(index, remaining)` (needs a map when values are large), meet-in-the-middle (O(2^(n/2))) for few large values, and a `BigInteger`/modular count when the answer overflows. Negative numbers need an offset.
- **D1:** Two `TreeSet`s of indices ordered by `(value, index)` give exact removal with duplicates in O(log k); two heaps with lazy deletion are faster in practice (no tree nodes) but need a balance counter and careful pruning of stale tops. An order-statistic structure (Fenwick tree over compressed values with binary descent, O(log n) per query) is the leanest: no per-element objects, great for streaming percentiles. For a very large k or approximate answers (p99 latency over a window) use t-digest/HdrHistogram buckets instead of exact medians. Overflow: `(double) a + b` before halving. Test with all-equal arrays and `k = n` and `k = 1`.
- **E:** `@OneToMany(mappedBy)` keeps the foreign key on the many side; the helper methods `addComment`/`removeComment` keep both sides consistent (JPA only looks at the owning side when writing). `orphanRemoval` deletes a row when it leaves the collection, `cascade` propagates persist/remove; neither replaces a database `ON DELETE CASCADE` for bulk deletes (`@Modifying` JPQL bypasses the persistence context). Fetch join answers "one task + its comments" in one query but cannot be combined with `Pageable` on the collection (Hibernate paginates in memory, warning HHH90003004): page the parents first, then load children with `IN (:ids)` or `@BatchSize`. Listing returns a summary DTO so no lazy collection is ever touched; `open-in-view: false` turns accidental lazy loading in the web layer into a loud error instead of N+1 queries. `Enum` mapping: `STRING` is safe against reordering, `ORDINAL` is not; a DB check constraint or a lookup table protects against bad data. Auditing needs `@EnableJpaAuditing` on a config class that slice tests can leave out. Sorting by a user-supplied field must be whitelisted (JPQL/Criteria injection and index-less sorts), with a unique tie-breaker (`id`) so pages do not overlap. Offset paging is O(offset): move to keyset when lists are deep. Validation of parameters (`@Positive`, `@Min`) is built into Spring 6.1 handler methods and produces `HandlerMethodValidationException`, which `ResponseEntityExceptionHandler` maps to a 400 ProblemDetail. Add an integration test on the real database dialect (Testcontainers); H2 hides locking, enum DDL and index differences.
- **F1 / G:** Store only `(sku, qty)` plus a few metadata fields; price is read at view time from the catalog (cached, TTL seconds) and re-validated at checkout, with the order service snapshotting the final price: this avoids stale-price bugs and keeps cart writes tiny. Redis hash per owner (`HSET cart:{id} sku qty`, `EXPIRE`) handles 20k writes/s trivially, and durability can be a write-behind to DynamoDB/Cassandra keyed by owner with TTL; SQL works for logged-in users but is the wrong default for guest carts (cardinality, churn). Two devices: per-line `HINCRBY`/conditional writes (or a version field) beat read-modify-write; last-write-wins on setQty is acceptable, but add a cart version header for conflict detection. Merge on login: idempotent (merge token) because mobile clients retry; cap quantities; choose the policy (sum, max, or prefer user) deliberately and tell the user. Hot keys are impossible per cart but the catalog price lookup is hot: batch `getPrices(skus)` and cache. Abandoned-cart and TTL: lazy expiry plus Redis expiry; for analytics emit events (CartUpdated) to Kafka instead of scanning. Failure modes: catalog down -> show last known price flagged "unverified" and block only checkout; cart store down -> degrade to a client-side cart. LLD notes: the per-owner monitor + copy-on-write mutation gives atomic "all or nothing" updates; locking two owners in sorted order avoids deadlock; at scale replace in-process locks with Redis Lua/`WATCH` or an optimistic version column.
- **F2:** Keep a per-product structure of watches sorted by threshold (a sorted set / bucketed by price band), so a price drop from p_old to p_new triggers exactly the watches with `p_new <= threshold < p_old`: a range scan, not a scan of all watchers. Only notify on the downward crossing (state per watch: `lastNotifiedPrice` or "armed" flag, re-armed when the price rises above the threshold), which also fixes flapping (999 -> 1100 -> 999 sends one alert per genuine drop, and a minimum interval or hysteresis avoids spam). For a viral product with 2M watchers, fan out in chunks through a queue partitioned by product (ordering per product), idempotency key `(user, product, priceEventId)`, and rate-limit per channel (APNs/FCM/SES quotas), with quiet hours and daily caps enforced at send time. Price events come from a Kafka topic keyed by product id; compact and coalesce rapid updates (only the latest price per product per second matters). Storage: watches in a sharded KV/Cassandra table by product with a secondary view by user (for "my watches" and deletes); counts and hot products are watched with metrics. Failure modes: duplicate or out-of-order price events (carry a version), notification provider outage (retry with backoff, dead-letter, drop stale alerts after N minutes because an old alert is worse than none), and a bad price feed (a seller sets 1 instead of 1000: add sanity checks/circuit breakers before fan-out).
- **H1:** rules behind each result: JLS 12.4/12.5 and 8.8.7 (class initialisation once; instance initialisers and field initialisers run after the super constructor returns, hence `v=0` seen through the virtual call), 5.1.7 and `IntegerCache` (-128..127), 15.28 and 3.10.5 (constant expressions are interned; non-final concatenation is not), 14.20.2 (finally completion overrides; return value computed before finally), the `hashCode` contract (never mutate hash-relevant fields of a key), 15.12.2 (three-phase overload resolution; static types), `AbstractList.modCount` (sublist invalidated by structural change of the parent), `PriorityQueue` is a binary heap (iteration order is the array order), `Arrays.asList` with a primitive array is `List<int[]>`, `LinkedHashMap(accessOrder=true)` counts `get` and `putIfAbsent` on an existing key as access.
- **H2:** Specification is a predicate with a name and a description, so rules can be reused, logged and explained ("why was this rejected?") and translated: the same tree can be interpreted into a JPA `Specification`/SQL `WHERE` by a visitor, which is how Spring Data keeps query logic out of services. Prefer plain `Predicate` composition (`and`, `or`, `negate`) when you do not need descriptions; add `explain(candidate)` returning the failing leaves when you do. PECS: `Spec<? super T>` as a parameter means a rule written for a supertype can be applied to subtypes; the result is `Spec<T>`. Deep chains of `and` build deep call stacks and slow evaluation (each node adds a virtual call): flatten `allOf` into an array loop. Make specs immutable and stateless so they are thread-safe and cacheable; anything with state (counters, clocks) must be injected. `@SafeVarargs` is only legal on static, final or private methods because overriding could break the guarantee that the varargs array is not exposed.
