## Principal-engineer review: follow-ups and how to make each design more efficient

- **A1 / A2:** Stock profit is the 1-transaction case of a DP family: ask for k transactions (O(nk) states buy/sell), a cooldown, or a fee, and know the "sum of all rises" answer for unlimited transactions. `containsNearbyDuplicate` with a hash map is O(n) space; the sliding-window `HashSet` of size k bounds memory to k, and for `abs(nums[i]-nums[j]) <= t` use a `TreeSet` (floor/ceiling) or bucketing by `value / (t+1)`. Merge-from-the-back is the same trick as in-place array compaction: write where nothing unread lives. For subsequence queries against one long `t` with many `s`, precompute `next[i][c]` (or per-letter index lists + binary search) for O(|s| log |t|) each. Palindrome II generalises to "at most k deletions" (edit-distance DP, O(nk)); `countAndSay` never grows beyond about 1.3x per term (Conway's constant) so building strings is fine, but use `StringBuilder`.
- **B1:** `teeing` is the answer to "I need two aggregates but the stream is single-use". `filtering` vs `stream.filter` differs for groups that become empty; `flatMapping` avoids materialising an intermediate list per group. Downstream collectors compose, but each level adds allocation: for hot paths a single loop with a `TreeMap` is faster and clearer. `partitioningBy` always yields both keys (no `getOrDefault`). `topN` via sort is O(m log m) per group; a bounded min-heap makes it O(m log n), and `Collectors.collectingAndThen` is where you would plug it. Parallel streams: only for large CPU-bound work, with associative, stateless combiners.
- **C1:** Fenwick vs segment tree: Fenwick is shorter and faster for invertible operations (sum, xor); a segment tree is needed for min/max, lazy range updates, or non-invertible merges. Build in O(n) by pushing to the parent. Extensions: 2D Fenwick, range-update/point-query (difference array), range-update/range-query (two Fenwicks), and offline counting problems (count of smaller numbers after self, inversions) by compressing coordinates. `RandomizedSet`: swap-with-last gives O(1) removal; with duplicates (multiset) keep a `Map<Integer, Set<Integer>>` of positions; weighted sampling needs a Fenwick or alias table. For concurrency, a lock around two structures is simplest; `getRandom` must not see a half-updated pair. `TimeMap`: the "non-decreasing timestamps" promise lets you append and binary search; without it use a `TreeMap` per key (O(log k) set) or a persistent structure. Retention: add TTL/compaction (keep one version per time bucket) before it eats memory; for a distributed version this is the shape of an MVCC store.
- **C2:** Every greedy needs an exchange argument. Jumps: the set of indices reachable in j jumps is a prefix `[0, end_j]`, so tracking the furthest reach is enough (BFS in disguise). Gas station: if the tank first goes negative at i starting from s, no start in `[s, i]` works (each of them reached i with a tank >= 0 from s, so starting there only gives less), so the next candidate is i+1; total >= 0 guarantees the final candidate completes the circle. Partition labels is interval merging with the last occurrence as the end. Know when greedy fails: coin change with arbitrary denominations, 0/1 knapsack, weighted interval scheduling (DP). Extensions: jump game with costs (Dijkstra/DP + monotonic deque), gas station with tank capacity (segment tree / two-pass), task scheduler (counting + idle slots), candy (two passes).
- **D1:** Pigeonhole: with n values spanning `max-min`, the largest gap is at least `ceil((max-min)/(n-1))`, so with bucket width below that the answer never lies inside a bucket and only bucket min/max matter. It is O(n) but with a bigger constant and memory than `Arrays.sort` (dual-pivot quicksort handles 2M ints in ~150 ms), so in production sort unless you are on a stream or the constraint is real. LSD radix sort (base 256 or 65536, 2-4 passes) is the other O(n) answer and is stable and simple. Overflow is the trap: `max - min` can reach 2^32-1, so use `long`. Related: "smallest range covering k lists", "first missing positive" (index as hash), "find duplicate" (cycle detection); for streaming, maintain a `TreeSet` and update the best gap in O(log n) per insert.
- **E:** `@Version` makes the database the arbiter: `UPDATE ... SET ..., version=version+1 WHERE id=? AND version=?`; zero rows -> `OptimisticLockingFailureException`. The service pre-check gives a precise 412 with the current version; the column still guards the race between check and flush. ETag/If-Match is the HTTP form of compare-and-swap; 428 forces clients to send it (otherwise last write silently wins), 412 means "reload and retry", whereas 409 means a state conflict that a retry will not fix (duplicate email). Prefer optimistic locking when conflicts are rare and the user would otherwise hold a lock across think time; use pessimistic locks (`@Lock(PESSIMISTIC_WRITE)`) for hot rows where retries would starve. Never expose the entity: the view record is the contract; `Page` JSON is unstable, hence the plain list (add a `Link`/`X-Total-Count` or a cursor). `Specification`s keep dynamic filters type-safe, but `LIKE '%x%'` cannot use a b-tree index: use a trigram/full-text index or a search engine, and escape `%` and `_` in user input. Offset pagination is O(offset): use keyset (`where (created, id) < (?, ?)`). Also: the unique constraint, not `existsBy`, is the real duplicate guard; lower-casing the email on write (and a functional unique index in production) beats `IgnoreCase` scans; `open-in-view: false` avoids lazy-loading in the view layer. `@MockBean` slices are fast, but add one `@SpringBootTest` + Testcontainers test against the production database dialect (H2 hides locking and index differences).
- **F1 / G:** Layout: 41 bits of ms is ~69.7 years, 10 bits = 1024 workers, 12 bits = 4096 ids per ms per worker (4M/s). Uniqueness depends entirely on distinct worker ids at any one time: assign them with a lease in ZooKeeper/etcd/DB row (heartbeat, expire after crash, never reuse a live id), or derive from pod ordinal in a StatefulSet; two workers with one id silently corrupt data, so fencing the lease matters more than the code. Clock risk: NTP can step the clock back; throw (as here), or wait out small drifts (< 5 ms), or persist the last timestamp and refuse to start before it; leap-second smearing helps. Time-ordered ids make inserts append-only in B-trees (good locality) but concentrate writes on the newest range/partition (hot shard in range-sharded stores such as Bigtable/HBase/DynamoDB sort keys): hash-prefix or bit-reverse the key for sharding while keeping the id for sorting. Alternatives: UUIDv7 (no coordination, 128 bits, time-ordered, bigger index), ULID, DB sequence/ticket server with batch allocation (id ranges leased per node: simple, gaps on restart, not time-sorted), Redis `INCR` (single point, durability caveats). Ids are not secrets and leak creation time and volume; do not use them as capabilities. LLD notes: `synchronized` is fine up to ~millions/s since the critical section is tiny; for more, shard generators per thread with distinct worker bits or use CAS on a packed `AtomicLong` (timestamp+sequence). Spinning when the sequence overflows burns CPU for at most 1 ms; sleeping is imprecise. Injecting the clock is what makes overflow and rollback testable.
- **F2:** Presence is high-write, low-value data: never persist it durably per heartbeat. Gateway nodes hold the connection; each heartbeat (every ~5-10 s, or the TCP/WebSocket liveness) refreshes `presence:{user}:{device}` in Redis with a TTL of ~2.5 heartbeats; "online" = any device key exists; "last seen" = a timestamp written on disconnect and at most every few minutes while online (write-coalescing keeps 100M users at a few 100 k writes/s). Fan-out: do NOT push every flip to every friend. Push only to users who currently have that contact on screen (subscription on view open, via the gateway holding the viewer's socket), and pull the rest lazily when a chat opens; for big groups show presence for at most N visible members. Flapping (mobile networks) is damped by a grace period before declaring offline (e.g. 30 s) and by debouncing transitions. After a gateway crash 100 k users lose their heartbeat at once: TTLs expire together, so add jitter to TTLs and let reconnect storms be rate-limited (backoff with jitter on clients). Multi-device: online if any device is, last-seen is the max. Privacy: enforce "hide last seen" and block lists on the READ path (the presence service checks the relationship) and never leak it via timing or via the "typing" channel. Under overload degrade first: drop presence updates, widen the TTL, stop pushing to non-visible contacts, serve stale. Storage: Redis cluster sharded by user id, plus Kafka for presence-change events consumed by the notification/analytics paths.
- **H1:** rules behind each result: JLS 12.5 (superclass constructor runs before subclass field initialisers, so an overridden method sees `null`/0), 8.3 and 15.11 (fields are not virtual: `p.name` uses the static type), 8.4.8.2 (static methods are hidden, not overridden), 14.20.3.1 (try-with-resources closes in reverse order, close failures are added with `addSuppressed` to the primary exception, catch and finally run after the resources are closed), `java.util.stream` laziness (each element flows through the whole pipeline, `limit` short-circuits), JLS 15.25 tables (`int : double` promotes to double; reference types are not promoted; a constant `int` representable in `char` keeps `char`; `char : int variable` becomes `int`; unboxing a null in the third operand throws NPE), 15.17 and 15.19 (integer division truncates toward zero, `%` takes the dividend's sign, shifts mask the distance), 5.1.3 (narrowing int -> byte keeps the low 8 bits; double -> int saturates), 15.18.1 (string concatenation is left to right), `ArrayList` iterator (`hasNext` is `cursor != size`, so removing the second-to-last element skips the CME check), `Arrays.asList` (fixed-size write-through), `List.of` (null-hostile, `contains(null)` throws), `TreeMap` (comparator, not `equals`, defines key identity).
- **H2:** Observer pitfalls are the interview content: lifetime (a strong reference from the bus keeps subscribers alive, so return a `Subscription` and consider weak references or scoped buses), re-entrancy (copy-on-write snapshot means a handler cancelled mid-delivery is skipped by the `cancelled` flag but a new subscriber misses the current event), ordering (guaranteed per publisher thread only), failure isolation (swallowing exceptions hides bugs: route them to an error handler or a `DeadEvent`-like `HandlerFailed`), synchronous delivery means a slow handler blocks the publisher (offer an executor-backed variant, with ordering per subscriber), and type routing cost (`isAssignableFrom` per handler per event: cache the handler list per event class and invalidate on subscribe/cancel, as Guava does). Compare with the alternatives: Spring `ApplicationEventPublisher`, `Flow`/reactive streams with backpressure, and a message broker when delivery must survive a crash.
