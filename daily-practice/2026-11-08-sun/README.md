## Principal-engineer review: follow-ups and how to make each design more efficient

- **A1 / A2:** Dutch flag generalises to 3-way quicksort partitioning (many equal keys: O(n) instead of O(n log n)) and to k colours via counting sort (O(n + k), needs a counter array) or repeated partitioning. `moveZeroes` as written writes every position twice; the swap-when-different variant minimises writes (matters for flash memory/large pages). "At most K duplicates" is the same one-liner with `a[w-K]`. RPN: parse once, push operands, right operand pops first; follow-ups: infix to RPN with the shunting-yard algorithm, error handling for malformed input (stack underflow, division by zero), `long` or `BigInteger` for overflow. MinStack: a parallel stack costs O(n) extra; the "store difference from min" trick saves it but needs `long` to avoid overflow and is easy to get wrong, so say so. Max stack needs a TreeMap/linked-list + heap to pop-max in O(log n). Two-stack queue: amortised O(1) but a single pop can be O(n), unacceptable for latency-sensitive code; use an array-backed ring buffer (`ArrayDeque`) in practice, and the "two stacks" idea survives in persistent (functional) queues and in concurrent designs where producers and consumers touch different stacks.
- **B1:** One traversal per method; `groupingBy(..., TreeMap::new, downstream)` beats sorting afterwards. `topSpendCategories` sorts every category per account: for huge cardinality use a bounded heap (O(m log n)) or an approximate sketch. Money as `long` cents with a single division at the end; never `double` sums. `toMap` with `maxBy` resolves duplicate keys without a second pass, and the composite key (here a string with a NUL separator) is a smell: a record `Key(account, category)` is safer and avoids string building. `partitioningBy` always has both keys; `groupingBy` never creates empty groups. For many accounts, group once and compute all aggregates with `Collectors.teeing` or a custom collector instead of re-streaming. Parallel streams only for large CPU-bound work with associative, stateless accumulators.
- **C1:** Dijkstra is O((V+E) log V) with a binary heap and lazy deletion (skip stale entries with `if (d > dist[u]) continue`); a Fibonacci heap is rarely faster in practice. Negative edges need Bellman-Ford (O(VE)) or Johnson's algorithm; negative cycles must be detected. For unit weights BFS is O(V+E); for weights in a small range, a bucket queue/Dial's algorithm. Bidirectional Dijkstra and A* (admissible heuristic, e.g. Manhattan/haversine) cut the search area on road graphs; contraction hierarchies precompute shortcuts for millisecond routing. Min effort path can also be solved with binary search on the answer + BFS (O(RC log H)) or union-find over edges sorted by weight (Kruskal-style: the answer is the weight that first connects start and end): same family as minimum bottleneck spanning tree. Cheapest flights is a layered shortest path: Bellman-Ford with k+1 rounds on a copy of the previous round (in-place relaxation silently allows more than k hops), or Dijkstra on states `(city, stops)`. Overflow: sum of weights can exceed `int`, so use `long` distances.
- **C2:** The 26-child array trie is fast but wastes memory on sparse nodes (26 refs * 8 bytes): use `HashMap<Character,Node>` for large alphabets/Unicode, a compressed (radix) trie to merge single-child chains, or a double-array trie / DAWG for dictionaries; for autocomplete keep the top-k completions per node. `erase` without pruning leaks nodes under churn: prune when `pass == 0` on the way back (recursive or with a stack of nodes), which is what makes memory proportional to live words. Prefix queries vs a sorted array + binary search: the trie wins on repeated, very long shared prefixes and on counts, the sorted array wins on memory and cache behaviour. Thread safety: copy-on-write nodes or lock striping by first character; immutable tries are trivially shareable. `longestBuildableWord` can also be a DFS over the trie following only `end` nodes (lexicographic order for free); `replaceWords` is a longest/shortest-prefix match, the same structure as an IP routing table (longest prefix match on a binary trie).
- **D1:** Hierholzer finds an Eulerian path in O(E): the stack holds the current trail, and a node is emitted when stuck, so the route comes out reversed. Smallest-lexicographic order is just "always take the smallest unused edge first" (a min-heap per node, or sort once and keep an index pointer: O(E log E) total with less allocation). The existence conditions are: connected (on edges) and, for a directed graph, out-degree equals in-degree everywhere except start (out = in + 1) and end (in = out + 1); validate input instead of trusting it in production. Naive DFS with backtracking is exponential in the worst case and recursion overflows the stack at 300k tickets. The same algorithm gives de Bruijn sequences and DNA assembly (Eulerian path over k-mers), and a Chinese-postman route in street-sweeping problems.
- **E:** `@ManyToMany` is almost always better modelled as an explicit join entity (`Enrollment` with its own id, `enrolledAt`, status, and a unique `(course, student)` constraint) the moment the relation has any attribute; it also avoids Hibernate's delete-all-and-reinsert behaviour for `List` mappings and makes "enroll" a single INSERT with no need to load the whole collection. Today's `course.getStudents().contains(s)` loads every student of the course: fine at capacity 500, wrong at 10^6; use `existsByCourseIdAndStudentId` or rely on the unique constraint. The capacity check is a race: two concurrent enrolments can both see a free seat. Fix with `@Lock(PESSIMISTIC_WRITE)` on the course row, an `@Version` column on Course (retry on `OptimisticLockingFailureException`), or a conditional atomic update (`update course set enrolled = enrolled + 1 where id = ? and enrolled < capacity`). Uniqueness checks via `existsBy...` are also racy; the database unique index is the real guarantee, so catch `DataIntegrityViolationException` and map it to 409. `size(c.students)` in a projection compiles to a correlated subquery: fine for a few hundred rows, otherwise keep a denormalised counter. Fetch join + `Pageable` on a collection makes Hibernate paginate in memory (HHH90003004): the list endpoint returns summaries that never touch `students`. Embeddable records work from Hibernate 6.2; remember columns are nullable unless declared. PATCH with `null = unchanged` cannot express "set to null"; use JSON Merge Patch with `JsonNullable` or `Optional` wrappers when that matters. The injected `Clock` makes time rules testable; use `LocalDate.now(clock)` with an explicit zone for the business timezone. Route order: the literal `/courses/enrollment-counts` beats `/courses/{id}` because Spring picks the more specific pattern, but a typo in the id type would turn it into a 400; keep such routes under a different prefix if in doubt. `@MockBean` is deprecated from Boot 3.4 in favour of `@MockitoBean`. Add Testcontainers tests for the real dialect (H2 hides locking and constraint differences).
- **F1 / G:** Core design: the idempotency record `(merchant, key) -> {fingerprint, state, lease/expiry, response, token}` written with one atomic operation before any side effect: Redis `SET key value NX PX lease` (or Lua), or a SQL `INSERT` guarded by a unique index, in the same database transaction as the payment when possible (then "charge recorded" and "key completed" commit atomically and the crash window disappears). When the PSP is external the window cannot be closed locally, so pass a derived idempotency key to the PSP (the PSP deduplicates) and make the recovery path "look up by key" before retrying. The lease plus fencing token handles a worker that stalls (GC pause, network partition): the takeover bumps the token and the stale worker's `complete` is rejected; the downstream write must also check the token (otherwise fencing is only advisory). Retention: store completed responses 24 h in Redis with TTL, long-term proof of payment lives in the ledger, not in the idempotency store. Fingerprint: hash of method + path + canonical body (not headers like Date); store the hash, not the body. Size the store: 20k RPS * 86 400 s * ~1 KB is about 1.7 TB/day if every request is a new key, which is why TTL and small records matter; shard by key hash; keep hot replicas in the same region as the API. Behaviour on store outage: for payments fail closed (503) rather than risk double charge; for low-risk operations fail open and rely on downstream dedupe. Multi-region active/passive: replicate asynchronously and accept that failover can lose the last seconds of keys, so the PSP-level key is the last line of defence. LLD notes: `ConcurrentHashMap.compute` makes each key transition atomic without a global lock; never call out to I/O inside `compute`; the `purgeExpired` scan should run on a schedule, or switch to a delay queue/`expireAfter` in Caffeine; the clock must be monotonic-safe in production (wall-clock jumps shorten or lengthen leases: prefer `System.nanoTime` for leases and wall time only for retention).
- **F2:** Frontier = front queues (priority by importance/freshness, PageRank-like scores) feeding back queues (one per host, drained no faster than that host's crawl delay), with a heap keyed by "next allowed fetch time" to pick a host. Partition hosts across workers by consistent hashing so one worker owns a host's politeness state; rebalance on membership changes. URL dedupe: normalise (lowercase host, strip fragments and default ports, sort/remove tracking params, resolve relative paths), then check a Bloom filter (about 10 bits per URL for 1% false positives: 10^10 URLs is about 12 GB sharded across workers) backed by a persistent store to recover from restarts; Bloom false positives mean some pages are never crawled, which is acceptable. Content dedupe: SimHash/MinHash fingerprints for near duplicates; canonical link headers. Spider traps: cap depth, URL length, per-host page budget, calendars with infinite next links; detect repeating path segments. Capacity: 10^9 pages per month is about 400 pages/s average; 1 MB average with compression stored as 100 KB gives 100 TB/month in object storage (S3/HDFS) with metadata (url, hash, timestamps, status) in a wide-column store; 400 pages/s * 1 MB is about 3.2 Gbit/s raw bandwidth, so plan many workers with async I/O. Re-crawl scheduling: estimate change rate per page from history and revisit proportionally, with `If-Modified-Since`/ETag to save bandwidth. Robots.txt cached per host with TTL (24 h), and honour `Crawl-delay`. Failure modes: DNS slowness (local resolver cache), slow servers (strict timeouts and max size), poisoned/huge responses, a crashed worker (its in-flight URLs return to the frontier through leases), headless-rendering costs for JS-heavy sites (separate, expensive pool).
- **H1:** rules behind each result: JLS 14.20.3 (try-with-resources: resources close in reverse order, close exceptions are added as suppressed to the primary one, catch and finally run after close), 15.25 (conditional operator: numeric promotion makes `true ? 1 : 2.0` a `double`, but a boxed/Object operand blocks it), 5.1.3 (narrowing casts keep low-order bits; `char += 1` has an implicit cast), 15.17 (integer division truncates, `%` keeps the sign of the dividend), `Math.abs(Integer.MIN_VALUE)` overflows, 5.1.3 for floating-to-int saturating casts, `Double.equals` uses bit patterns, `List.remove(int)` vs `remove(Object)`, `Collections.unmodifiableList` is a live view, `Arrays.asList` is fixed size, `List.of` rejects null even in `contains`, `subList` throws `ConcurrentModificationException` after the parent is structurally modified, JLS 8.3 (fields are hidden not overridden; static and private methods are not virtual), 15.12.2 (overload resolution phases: strict/widening, then boxing, then varargs), `String.split` drops trailing empty strings, `replaceAll` takes a regex, streams are lazy and processed one element at a time through the whole pipeline until a short-circuit, `sorted()` is a full barrier, a stream cannot be reused.
- **H2:** Command = reversible operation as an object; the interesting design points are what state the command captures at `execute` time (the deleted text), idempotence of redo (re-capture on every execute), and atomic composite commands (compensate the executed prefix, in reverse order). Memento (snapshot of the whole document) is simpler but O(n) memory per step; commands store deltas, so history costs O(change). For collaborative editing the same idea evolves into operational transformation or CRDTs, where commands must be transformed against concurrent ones. A bounded history uses a deque; coalescing consecutive keystrokes into one undo step needs a `merge(Command)` method. Thread safety: either confine the editor to one thread or make `run/undo/redo` synchronized; commands themselves are stateful (`DeleteCommand.removed`), so one command instance must never be shared across editors. `StringBuilder.delete` clamps silently, so validate ranges yourself; for large documents use a rope or piece table instead of a flat buffer to keep inserts O(log n).
