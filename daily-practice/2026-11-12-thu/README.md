## Principal-engineer review: follow-ups and how to make each design more efficient

- **A1 / A2:** Roman: the right-to-left scan needs no look-ahead (a symbol smaller than its right neighbour is subtracted); the greedy table with the six subtractive pairs is the inverse and is O(1) because the output is at most 15 symbols. Follow-up: validate input (repeat limits, illegal pairs like `IL`) by round-trip `intToRoman(romanToInt(s)).equals(s)`. Common prefix: vertical scan is O(total prefix work) and stops at the first mismatch; sort-and-compare-first-last is O(n log n * L) but fine for a few strings; for many strings or repeated queries build a trie (see G). Spiral: four bounds shrinking, and the two `if` guards before the bottom row and left column are exactly what a single row/column needs; an alternative is direction vectors with a visited marker (simpler to reason about, O(mn) extra). Rotate = transpose then reverse rows (counter-clockwise: reverse columns, or reverse rows first); the four-cell cycle swap does it in one pass with better locality. Toeplitz on a stream of rows only needs the previous row (O(n) memory), and on a matrix too big for memory you load one row plus the prior row at a time.
- **B1:** one collector chain each; `groupingBy(f, TreeMap::new, downstream)` for ordered keys; `teeing` computes two independent reductions in a single pass (`filtering` inside it keeps the predicate next to its sum). `busiestWarehouse` is a nested `groupingBy` and a `max` with an explicit tie-break comparator, never rely on `HashMap` order. The reduction is O(n) plus a sort over distinct SKUs; for data that does not fit in memory this is a keyed aggregation (stock per SKU as a running state in a stream processor), and negative stock is a data-quality alert, not a report.
- **C1:** DSU with path halving and union by size is O(alpha(n)) amortised, O(n) space; plain path compression alone is O(log n) amortised, no compression and no rank can degrade to O(n) per find (the 200k chain test). `findRedundantConnection` processes edges online, the first edge whose endpoints already share a root closes the cycle, which is also the last such edge in a tree + 1 edge input. Provinces is O(n^2) just to read the matrix; with an edge list it is O(E alpha). Accounts merge: map each email to its first owner, union owners on collision, then bucket emails by root (TreeSet gives sorted output); total O(E log E) for the sorting, `E` = emails. Offline connectivity with deletions needs a different structure (offline divide and conquer over time with a rollback DSU); streaming connectivity at scale is a union-find on a sharded key space with periodic compaction.
- **C2:** all four are sort + sweep. Merge sorts by start so a single "current end" decides overlap; closed intervals merge on `cur.start <= last.end`, half-open ones on `<`. `insert` is the three-phase scan (before, overlapping, after), O(n) because the input is already sorted; with many inserts keep a `TreeMap<start, end>` and merge neighbours in O(log n). Meeting rooms: sorted starts and ends with two pointers (an end at time t frees the room before a start at t), or a min-heap of end times (also gives the room assignment); a sweep over +1/-1 events generalises to "max overlap". `eraseOverlap` is the interval-scheduling greedy: keep the interval that ends first, which leaves the most room; sorting by start and keeping the earlier end on conflict is equivalent. Compare with `Integer.compare` or use a `long`, subtraction overflows near the int limits.
- **D1:** `dp[l][r]` = best coins for the open range (l, r) when `l` and `r` stay; choose the LAST balloon `k` burst inside: its neighbours are then exactly `l` and `r` and the two sides are independent subproblems. Choosing the first balloon breaks independence because neighbours change. O(n^3) time, O(n^2) space; the answer for n = 300 and all 100s is 298,010,100, which fits in `int` (the largest term is 10^6, at most 300 terms) but note `long` if the bounds grow. The same "last operation" trick solves matrix-chain multiplication, minimum cost to cut a stick and remove-boxes variants. Top-down memoisation touches only reachable ranges but the recursion is 300 deep, fine on the JVM; bottom-up by length is cache-friendlier.
- **E:** the unique constraint is the real guard against duplicates: the service's `existsBy...` gives a friendly early 409 but two concurrent requests can both pass it, so the constraint violation (`DataIntegrityViolationException`, thrown at flush/commit, so it can surface after the service method returns) is mapped to the same 409. The composite index `(product_id, status, created_at)` serves the list query; the `id desc` tie-break makes offset pages stable, but offset is O(offset): use keyset paging (`created_at < :c`) and skip `count(*)` for big products. Aggregates by `avg`/`group by` scan every review of a product on each call: at scale keep a `product_rating_summary` row (count, sum, histogram) updated in the same transaction (or by events) and use the query only as the repair job. `avg` returns `Double` (null when empty), never unbox it. The interface projection selects only two columns, no entity hydration. `@ConfigurationProperties` records are immutable, relaxed-binding (`banned-words` to `bannedWords`) and validated at startup, so a bad config fails the deploy instead of the first request; `@Value` is fine for one number. Banned words by `contains` is naive (Scunthorpe problem, unicode tricks): move moderation async (status `PENDING` then a moderation service), keep the synchronous path cheap. `@ResponseStatus` is convenient for exceptions you own; `ProblemDetail` via `@ExceptionHandler` carries a body and is better for public APIs; extending `ResponseEntityExceptionHandler` makes framework errors consistent. Read-only `@Transactional` lets Hibernate skip dirty checking and routes to replicas in some setups. IDOR: ownership check returns 403 here; returning 404 for other people's rows hides existence.
- **F1 / G:** serve suggestions from a precomputed structure, not from the live query log: an offline/streaming job (Flink/Spark) aggregates queries with a time-decayed count (e.g. exponential decay or hourly buckets with weights), filters through the blocklist and a quality gate (min count, min distinct users to resist spam), then writes `prefix -> top-k` for every prefix up to length ~8 into a KV store (Redis/DynamoDB) or ships a compact trie/FST snapshot to the serving fleet; read path = one key lookup, no computation. Cache at the CDN keyed by prefix (short TTL, 1-2 chars are the hottest and most cacheable), debounce and cancel stale requests on the client, and only call the server from the 2nd character. Fresh trends: a small "hot" overlay updated every minute merged at read time with the daily-built base. Typos: fall back to an n-gram or edit-distance index (BK-tree/SymSpell) only when the prefix lookup is empty. Personalisation is a re-rank of the top 20-50 on the edge using the user's recent history, never a per-user trie. Privacy: do not log or learn from queries that look like emails, card numbers or are rare; k-anonymity threshold. G detail: the trie node count is the memory cost, so intern or cap depth/length; per-node cached top-k makes reads O(L) and writes O(L*k), a good trade for read-heavy typeahead; one `ReadWriteLock` is fine for the exercise, for a hot service build a new immutable snapshot and swap an `AtomicReference` (readers never block).
- **F2:** treat delivery as a queue per endpoint, not per event: events are written to a durable log (outbox in the payments DB, then Kafka) and a fan-out step creates one delivery row per (event, endpoint) with state, attempt, `next_attempt_at`. Workers pull due deliveries with a lease (`SELECT ... FOR UPDATE SKIP LOCKED` or a delay queue), POST with a short timeout (5-10 s), and on non-2xx/timeout reschedule with exponential backoff and jitter (e.g. 1 min, 5 min, 30 min, 2 h, ... up to 3 days) then mark `DEAD` and surface it in the dashboard; replay is just resetting the row. Isolation: per-endpoint concurrency limits and a circuit breaker (open after N consecutive failures, probe with one request) so a hung merchant occupies a bounded number of workers; bulkhead by hashing endpoints to worker pools. Signing: `HMAC-SHA256(secret, timestamp + "." + body)` in a header, the merchant rejects timestamps older than 5 min and de-duplicates by event id (at-least-once means duplicates); support two active secrets during rotation. SSRF: resolve DNS yourself, block private/link-local/metadata ranges, pin the resolved IP for the connection, no redirects, https only. Ordering is intentionally weak: include a monotonically increasing `sequence` or the object's version so merchants can discard stale updates, or offer an ordered mode that serialises one endpoint's queue (head-of-line blocking, so make it opt-in). Capacity: 20k events/s times about 3 endpoints each is 60k deliveries/s; at 1 KB bodies that is 60 MB/s outbound, with at most ~30 s per attempt you need roughly 60k * 0.2 s average = 12k concurrent connections, so use async IO or virtual threads. Observability: delivery latency percentiles, success rate per endpoint, queue age; auto-disable endpoints failing for days and email the owner.
- **H1:** s1 JLS 12.4.1: reading a constant variable (`static final` primitive/String initialised by a constant expression) does not initialise the class; `Config.LOG` triggers `Config` init only; `Lazy.COMPUTED` is not a constant so reading it triggers `Lazy`'s static block; `static final Integer` is not a constant variable. s2 JLS 15.29: `"ja" + "va"` and `final String fja + "va"` are constant expressions (interned, `==` true); a non-final local concatenation is computed at run time (new object); `new String` is a new object but `intern()` returns the pooled one; `"" + 1 + 2` is `"12"`, `1 + 2 + ""` is `"3"`, `'a' + 'b' + "c"` is `195c` because char + char is int addition. s3 JLS 10.5/4.8: `String[]` is a subtype of `Object[]` so the store compiles and fails at run time with `ArrayStoreException: java.lang.Integer`; generics are erased so the unchecked add succeeds, the compiler-inserted cast in `String s = strings.get(0)` fails later; `ArrayList<String>` and `ArrayList<Integer>` share one `Class`. s4: `remove(1)` removes index 1, `remove(Integer.valueOf(1))` removes the value; `Arrays.asList` is fixed-size but writable and write-through; `subList` is a view (writes show in the base); removing in a for-each throws `ConcurrentModificationException` except when removing the second-to-last element (then `hasNext()` is false and the loop ends, the quirk); `List.of(..).contains(null)` throws NPE; `HashMap.containsKey` is true for a null value, `getOrDefault` returns the null (key present), `computeIfAbsent` treats null as absent. s5: the stream is lazy and `findFirst` short-circuits (elements 3 and 4 never reached, and `built` is logged first); `orElse` evaluates its argument eagerly, `orElseGet` only when empty; the loop lambdas capture an effectively final copy; the counter array is the escape hatch for mutable capture. s6: resources close in reverse order, a failing close during an exception is added with `addSuppressed` (primary stays `body-fail`), a failing close with no primary exception becomes the exception thrown (and `getSuppressed().length` is 0); `finally` runs after the catch.
- **H2:** the common bug is a mutable `index` field in the pipeline (not thread-safe, and broken by a second `proceed` or by re-entrancy). Putting the position in an immutable `Chain` object created per link makes the pipeline stateless, so `retry` can call `proceed` again and many threads can share one instance. The cost is one small allocation per handler per call; if profiling shows it, precompute the chain once by folding the handlers from the end (`next = (req) -> h.handle(req, next)`), which allocates once at construction and is also stateless. Depth equals the handler count on the stack (servlet filters, Netty pipelines and OkHttp interceptors do the same); async variants return `CompletionStage<S>` and need care with exceptions thrown before the stage is created. `List.copyOf` gives the defensive copy and the null check in one call. Real middleware adds ordering annotations, per-route chains and short-circuit metrics; the Decorator pattern is the same shape with a fixed interface, Chain of Responsibility emphasises "may stop the request".
