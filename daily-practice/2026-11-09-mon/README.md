## Principal-engineer review: follow-ups and how to make each design more efficient

- **A1 / A2:** `twoSum` on a sorted array drops to two pointers with O(1) space; for streams of numbers keep the map but bound memory. Anagram keys: a 26-count signature is O(k) per word versus O(k log k) sorting, but only for a fixed alphabet (use sorted code points for Unicode, and normalise first: NFC and case). Boyer-Moore needs a verification pass when a majority is not guaranteed, and generalises to "more than n/k" with k-1 counters (Misra-Gries, also a streaming heavy-hitters sketch). `countPrimes`: odd-only or a bitset sieve cuts memory 16x, a segmented sieve keeps it cache-friendly beyond 10^9; `gcd` via binary GCD avoids division; `isHappy` has a fixed small cycle (4 -> 16 -> 37 -> 58 -> 89 -> 145 -> 42 -> 20 -> 4), so "reaches 1 or 4" is O(1) space without Floyd.
- **B1:** One traversal per method. `topDriverByCity` builds a per-driver map per city; for huge cardinality keep a bounded heap or a single `toMap` merge keyed by `(city, driver)` and then reduce. `partitioningBy` is a two-bucket `groupingBy` with both keys guaranteed. `takeWhile`/`dropWhile` are only meaningful on ordered streams (on unordered or parallel streams the result is nondeterministic) and short-circuit. Money stays `long` cents; averages are computed once at the end, never averaged twice.
- **C1:** Binary search on the answer is O(n log(hi - lo)); the check is a greedy scan, which is correct because the predicate is monotonic. Tighten the bounds (`lo = max element`, `hi = sum`; for bananas `lo = ceil(sum / h)`) to save iterations. For many queries with different k, precompute prefix sums and do the check with binary searches (O(k log n) per probe). `splitArray` also has an O(n^2 k) DP that supports extra constraints (cost functions that are not a plain sum) where the greedy check no longer applies; Knuth/divide-and-conquer optimisation brings it to O(k n log n). Use `long` for sums and `lo + (hi - lo) / 2`.
- **C2:** Kadane is a DP with O(1) state: `best ending here`. The circular case is max(normal, total - minimum subarray) with the all-negative exception; the alternative is Kadane on the doubled array with a window limit of n (monotonic deque over prefix sums, O(n)). Max product needs both extremes because a negative swaps them; a zero resets. For "return the indices" keep the start of the current run. With very large inputs products overflow: use `BigInteger`, logs (precision loss), or split at zeros and reason about the parity of negatives. Parallelise Kadane by treating each chunk as a (total, best prefix, best suffix, best) monoid and combining.
- **D1:** Merge sort counting is O(n log n) time, O(n) space, no recursion depth problem (log n). A Fenwick tree over compressed values is also O(n log n) and handles an online stream (insert from the right, query the prefix); an order-statistic tree gives the same. Ties must not count as smaller: take the left element first on equality. Variants with the same skeleton: count inversions, reverse pairs (`a[i] > 2 * a[j]`, needs a separate counting pass before the merge) and count of range sums on prefix sums. Allocate the temp array once (done) to avoid GC churn on large n.
- **E:** `@ElementCollection` is right for small value collections owned by one parent; the collection table has no id, so Hibernate cannot update single rows by identity: without `@OrderColumn` a removal deletes all rows and re-inserts the rest, with it only the tail is rewritten. If lines need their own lifecycle, ids or queries across invoices, model an `InvoiceLine` entity with `@ManyToOne`. The JPQL constructor expression returns DTOs directly (no managed entities, no dirty checking); an interface projection is the alternative. The `@Modifying` update bypasses the persistence context and `@Version`/auditing, so it needs flush before and clear after, and it will not fire entity listeners. Transitions here are last-write-wins: add `@Version` (optimistic lock, 409 on `ObjectOptimisticLockingFailureException`) or an atomic `update ... where status = :expected` for real concurrency. Offset paging degrades with depth: use keyset pagination (`id > :last`) for big tables, and the `Page` total count query can be dropped with `Slice`. Return money as integers (cents) and keep currency explicit.
- **F1 / G:** Core design: code = Base62 of a unique id (counter ranges leased per app server, or Snowflake) so there are no collisions and no lookup before insert; 7 characters give 62^7 = 3.5 trillion codes; random codes need a collision retry and are unguessable, sequential ones leak volume and are enumerable (add a permutation/Feistel step if that matters). Storage: key-value (DynamoDB/Cassandra/sharded SQL) keyed by code, around 500 bytes per link: 100M/month means about 600 GB/year, small. Reads dominate: CDN plus local LRU plus Redis, with 301 cached by browsers (cheap, but later clicks are invisible and edits do not propagate) versus 302 (every click hits you: analytics-friendly). Count clicks asynchronously: append events to Kafka, aggregate per (code, minute) in a stream job into a time-series store; per-instance `LongAdder`s flushed periodically absorb hot links; the exact in-memory counter in G is the single-node core of that. Custom aliases use a conditional insert (unique key) and share the namespace with generated codes, so the generator must skip taken codes (G does). Expiry: lazy check on read plus a background sweep (TTL index). Abuse: rate limit creates per API key, URL scanning/blocklists, no open redirects to `javascript:` (G restricts to http/https).
- **F2:** Seat state machine AVAILABLE -> HELD(until, holder) -> SOLD, with the hold done as one atomic conditional write (`UPDATE seat SET state='HELD', until=? WHERE id=? AND (state='AVAILABLE' OR until < now())`, or Redis `SET seat NX PX`) so two buyers can never both win. Expiry by TTL plus a sweeper; the money path must be idempotent: `confirm(holdId)` succeeds only if the hold is still the buyer's, and a late payment on an expired hold is refunded or re-acquires the seat if still free. Contention: shard by event and seat block, keep the hot path in a single-writer partition per event (actor-style) instead of distributed locks; serve the seat map from a cache with a short TTL (stale reads are fine, the write path decides). A virtual waiting room (token bucket admitting N users/s, signed queue tokens) protects the checkout; per-user limits and bot protection matter as much as the database.
- **H1:** rules behind each result: JLS 12.4/12.5 (static initialisers run once per class on first use, superclass first; instance initialisers and field initialisers run in textual order after `super()` returns, and a virtual call from the super constructor sees default field values, but a `final` field with a constant initialiser is already inlined), 14.20.2 (`finally` runs after the return value is computed, so `i = 99` is invisible but a mutation of a returned array is visible; a `return` in `finally` discards exceptions), 5.1.7 (`Integer` cache -128..127 only, `Long.equals(Integer)` is false, `Double.equals` uses bits: `0.0` differs from `-0.0` and `NaN` equals `NaN`), 15.12.2 (overload phases: widening before boxing before varargs; `char` widens to `long`), `ArrayList` iterator's `hasNext()` is `cursor != size`, which is why removing the second-to-last element hides the `ConcurrentModificationException`.
- **H2:** The ring buffer is the textbook structure for bounded logs and streaming windows: O(1) add/evict with no shifting; make capacity a power of two to replace `%` by a mask. The fail-fast iterator is best-effort (it throws when it notices, not guaranteed); `modCount` is the same mechanism as `ArrayList`. `equals/hashCode` must depend only on the logical sequence, and a mutable collection as a `HashMap` key is a trap (see H1 s4). For concurrency do not synchronise `get` and `add` separately: single-producer/single-consumer rings can be lock-free with two volatile indices (Disruptor), multi-producer needs CAS or a lock. Consider implementing `Collection`/`SequencedCollection` (Java 21: `getFirst/getLast/reversed`) and returning a snapshot spliterator for streams.
