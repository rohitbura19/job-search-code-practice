# Q09. Mini Instagram: core LLD + schema + API

**Duration:** 40 minutes (20 for code, 20 for design) · **Language:** Java · **Source:** IDFC L1 round, per LeetCode ("design basic Instagram: DB choice, API design, schema")

## Part A: Code (in memory)

```java
class SocialService {
    void createUser(String userId)                 // duplicate -> IllegalArgumentException
    void follow(String follower, String followee)  // self-follow -> IllegalArgumentException; idempotent
    void unfollow(String follower, String followee)
    long post(String userId, String caption)       // returns a postId; ids increase with time
    void like(String userId, long postId)          // idempotent: liking twice counts once
    int likeCount(long postId)
    List<Long> feed(String userId, int k)          // the latest k posts by the user AND the people they follow, newest first
}
```

### Example

```
createUser A, B, C
follow(A, B)
p1 = post(B, "hello")      p2 = post(C, "sunset")      p3 = post(A, "coffee")
feed(A, 10) -> [p3, p1]
follow(A, C)
feed(A, 10) -> [p3, p2, p1]
unfollow(A, B)
feed(A, 10) -> [p3, p2]
like(A, p2); like(A, p2)
likeCount(p2) -> 1
feed(A, 1) -> [p3]
```

### Expected

- `Map<String, Set<String>> following`, `Map<String, Deque<Post>> postsByUser` (newest first), and `Map<Long, Set<String>> likes`.
- Build the feed by a **k-way merge with a max-heap** over each followee's newest posts: O(k log F), not "collect everything and sort".

## Part B: Design talk

1. **Schema:** `users`, `follows(follower_id, followee_id, created_at, PK(follower, followee))`, `posts(id, user_id, caption, media_url, created_at)`, `likes(post_id, user_id, PK(post_id, user_id))`. Which indexes?
2. **Database choice:** relational for users and follows, with a wide-column or key-value store for feeds and likes at scale. Be ready to justify it. (One candidate picked NoSQL because transactions weren't needed. Expect pushback.)
3. **APIs:** `POST /posts` (upload media to object storage with a pre-signed URL, then create the post), `GET /feed?cursor=…&limit=20` with cursor paging rather than offset, and `PUT /posts/{id}/like`.
4. **Fan-out on write vs on read**, and the celebrity problem (hybrid: pull posts from celebrities at read time).
5. **Like counter at scale:** async counting through a queue such as AWS SQS, then batch updates to the count.
6. Media: S3 and a CDN, thumbnails generated by a Lambda on upload.
